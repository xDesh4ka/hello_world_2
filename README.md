# Лекция 1. Часть 1. Как устроен веб

# 1. Клиент и сервер

## 1.1. Общая модель

В основе веба лежит клиент-серверная модель взаимодействия. **Клиентом** называется сторона, которая инициирует запрос и заинтересована в получении ресурса либо выполнении операции, а **сервером** — сторона, которая принимает этот запрос, выполняет необходимые действия и формирует ответ.

В большинстве привычных сценариев клиентом выступает браузер:

```
Пользователь
    ↓
Браузер — клиент
    ↓ HTTP-запрос
Веб-сервер — сервер
    ↓ HTTP-ответ
Браузер
```

Например, когда пользователь вводит адрес сайта и нажимает Enter, браузер не «открывает файл» в бытовом смысле этого слова. Он инициирует сетевое взаимодействие: определяет, с каким сервером нужно связаться, формирует HTTP-запрос и передаёт его серверу. Сервер анализирует запрос и возвращает HTTP-ответ, содержащий HTML-документ, данные API, изображение, CSS-файл или сообщение об ошибке.

HTTP является протоколом прикладного уровня, предназначенным для передачи ресурсов и организации взаимодействия между клиентом и сервером; при этом запросы инициируются клиентом, а ответ формируется сервером.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)]

## 1.2. Клиент — это не только браузер

Хотя в учебных примерах клиентом обычно называют браузер, это понятие шире. Клиентом может быть:

- мобильное приложение;
- другой сервер;
- консольная утилита;
- поисковый робот;
- скрипт на JavaScript;
- программа для тестирования API, например Postman или `curl`.

Следовательно, backend не должен предполагать, что с ним всегда разговаривает человек через визуальный интерфейс. Он взаимодействует с программами, которые отправляют запросы в соответствии с определённым контрактом.

Например, один и тот же endpoint:

```
GET /api/products
```

может быть вызван:

- браузером при открытии страницы каталога;
- frontend-кодом через `fetch`;
- мобильным приложением;
- автоматическим тестом;
- другим сервером.

Для backend существенны не внешний вид клиента, а метод запроса, URL, заголовки, параметры, тело запроса и контекст безопасности.

## 1.3. Сервер — это не обязательно один компьютер

В разговорной речи сервером часто называют физический компьютер, однако в веб-разработке это слово может обозначать несколько разных вещей:

1. компьютер или виртуальную машину, на которой выполняется программа;
2. серверное приложение, принимающее сетевые соединения;
3. программный компонент, реализующий конкретную бизнес-логику;
4. инфраструктуру из нескольких машин, распределяющих нагрузку.

Когда мы говорим «сервер обработал запрос», обычно имеется в виду не только аппаратная машина, но и совокупность программных компонентов:

```
Интернет
   ↓
Reverse proxy / балансировщик
   ↓
Backend-приложение
   ↓
Сервисный слой
   ↓
База данных
```

В небольшом учебном проекте всё это может находиться на одном компьютере и запускаться несколькими командами. В промышленной системе компоненты могут быть разнесены по разным контейнерам, виртуальным машинам или дата-центрам.

## 1.4. Промежуточные компоненты

Между браузером и приложением могут находиться промежуточные участники:

- DNS-серверы;
- маршрутизаторы;
- прокси;
- CDN;
- балансировщики нагрузки;
- кэши;
- межсетевые экраны;
- системы мониторинга и фильтрации.

При этом браузер логически взаимодействует с сервером назначения, хотя фактический сетевой путь может проходить через множество устройств. HTTP-уровень скрывает значительную часть нижележащей инфраструктуры, что позволяет разработчику мыслить категориями запросов, ответов и ресурсов, не описывая каждый маршрутизатор на пути пакета.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)]

# 2. Браузер

## 2.1. Браузер как клиент и среда выполнения

Браузер — это не просто программа для отображения текста и картинок. Он одновременно является:

- HTTP-клиентом;
- интерпретатором HTML;
- движком CSS;
- средой выполнения JavaScript;
- хранилищем данных;
- посредником между веб-приложением и устройством пользователя;
- инструментом сетевой безопасности;
- средой доступности для вспомогательных технологий.

Когда браузер загружает страницу, он выполняет сложную последовательность операций:

1. принимает адрес;
2. определяет сервер;
3. устанавливает защищённое соединение;
4. отправляет HTTP-запрос;
5. получает HTML;
6. разбирает HTML;
7. обнаруживает внешние ресурсы;
8. отправляет дополнительные запросы;
9. загружает CSS, JavaScript, изображения и шрифты;
10. строит внутренние структуры документа;
11. рассчитывает расположение элементов;
12. рисует результат на экране;
13. запускает обработчики пользовательских действий.

Поэтому HTML-страница не является готовой картинкой, которая целиком передаётся пользователю. Она представляет собой описание документа, из которого браузер строит интерактивное представление.

## 2.2. Браузер как ограниченная среда

JavaScript выполняется внутри браузера и не получает неограниченный доступ к компьютеру пользователя. Браузер намеренно ограничивает возможности веб-кода, чтобы одна открытая вкладка не могла произвольно прочитать файлы пользователя, включить камеру или отправить данные от имени другой вкладки.

Такие ограничения являются частью модели безопасности браузера. Например:

- доступ к камере обычно требует разрешения пользователя;
- веб-страницы разделены по происхождению;
- запросы к другому источнику ограничиваются политикой CORS;
- доступ к локальным файлам ограничен;
- опасные операции должны выполняться через специальные API и разрешения.

Для разработчика это означает, что браузер одновременно является мощной платформой и средой с жёсткими правилами. Веб-приложение должно работать в условиях, когда заранее неизвестны операционная система, размер экрана, браузер, скорость сети, доступные устройства и настройки приватности пользователя.

# 3. HTTP как язык взаимодействия

## 3.1. Что такое HTTP

**HTTP**, или HyperText Transfer Protocol, — это протокол обмена сообщениями между клиентом и сервером. Вопреки названию, он давно используется не только для передачи гипертекста: через HTTP передаются HTML-документы, изображения, видео, CSS, JavaScript, JSON и другие данные.

HTTP задаёт правила:

- как клиент сообщает, что ему нужно;
- как сервер сообщает результат;
- где указываются метаданные;
- как передаются данные;
- как обозначается ошибка;
- как клиент и сервер договариваются о формате содержимого.

В упрощённом виде взаимодействие выглядит так:

```
Клиент: «Дай мне ресурс по этому адресу»
Сервер: «Вот ресурс» или «Я не могу выполнить запрос»
```

Однако HTTP не является языком бизнес-логики. Он не знает, что такое «товар», «заказ» или «пользователь». Он предоставляет универсальный транспорт и набор семантических правил, на которых приложение строит собственные операции.

## 3.2. HTTP — протокол запросов и ответов

HTTP использует модель request-response:

```
HTTP request  →  сервер
HTTP response ←  сервер
```

Запрос и ответ являются самостоятельными сообщениями, каждое из которых содержит служебную часть и, при необходимости, передаваемые данные.

Общая структура HTTP-сообщения:

```
Стартовая строка
Заголовки

Тело сообщения
```

Между заголовками и телом находится пустая строка, которая отделяет метаданные от содержимого.

Для запроса:

```
Метод + путь + версия HTTP
Заголовки

Тело запроса
```

Для ответа:

```
Версия HTTP + статус-код
Заголовки

Тело ответа
```

В HTTP/1.1 эти сообщения удобно изучать в текстовом виде. В HTTP/2 и HTTP/3 данные передаются с использованием более эффективных внутренних механизмов, однако смысл методов, заголовков, статус-кодов и тела сообщения для разработчика сохраняется.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages)]

# 4. HTTP-запрос

## 4.1. Пример запроса

Рассмотрим условный запрос:

```
GET /catalog/anime?genre=fantasy&page=2 HTTP/1.1
Host: example.com
Accept: text/html
Accept-Language: ru
User-Agent: Mozilla/5.0
```

В нём присутствуют:

- метод `GET`;
- путь `/catalog/anime`;
- query-параметры `genre=fantasy` и `page=2`;
- версия протокола `HTTP/1.1`;
- заголовок `Host`;
- заголовок `Accept`;
- заголовок `Accept-Language`;
- заголовок `User-Agent`.

## 4.2. Метод

Метод указывает, какую операцию клиент хочет выполнить. Метод не является просто техническим названием endpoint’а: он передаёт семантику намерения клиента.

Например:

```
GET /api/anime
```

означает запрос на получение данных, тогда как:

```
POST /api/anime
```

обычно означает отправку данных для создания нового ресурса.

## 4.3. Адрес ресурса

Путь указывает, какой ресурс должен обработать сервер:

```
/api/anime
/api/anime/42
/api/users/15
```

Путь `/api/anime` обычно обозначает коллекцию, а `/api/anime/42` — конкретный объект с идентификатором `42`.

## 4.4. Заголовки

Заголовки передают метаданные о запросе. Они не являются основным содержимым операции, однако сообщают серверу важный контекст:

```
Content-Type: application/json
Accept: application/json
Authorization: Bearer <token>
Cookie: session_id=abc123
```

Примеры назначения заголовков:

- `Content-Type` сообщает формат тела запроса;
- `Accept` сообщает, какие форматы ответа подходят клиенту;
- `Authorization` передаёт сведения для аутентификации;
- `Cookie` передаёт идентификаторы сессии;
- `User-Agent` описывает клиент;
- `Origin` сообщает источник запроса;
- `Cache-Control` влияет на кэширование.

Важно различать `Content-Type` и `Accept`. Первый описывает то, что клиент отправляет, второй — то, что клиент готов принять.

## 4.5. Тело запроса

Тело запроса используется для передачи данных серверу. Оно чаще всего применяется в `POST`, `PUT` и `PATCH`.

Пример JSON-тела:

```
POST /api/anime HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "title": "Fullmetal Alchemist",
  "year": 2003,
  "genre": "fantasy"
}
```

Без заголовка `Content-Type: application/json` сервер может не понять, как интерпретировать переданные данные.

Тело может содержать:

- JSON;
- данные HTML-формы;
- `multipart/form-data`;
- бинарный файл;
- обычный текст;
- другой согласованный формат.

HTTP-сообщение не обязано всегда иметь тело. Например, у большинства запросов `GET` тело отсутствует, а запрос `DELETE` обычно передаёт идентификатор ресурса в URL.

# 5. HTTP-ответ

## 5.1. Пример ответа

```
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

{
  "items": [
    {
      "id": 42,
      "title": "Fullmetal Alchemist"
    }
  ]
}
```

Ответ состоит из:

- версии HTTP;
- статус-кода;
- краткого текстового описания;
- заголовков;
- тела ответа.

Статус-код является машинно читаемым результатом операции, а текстовое описание предназначено главным образом для человека. В прикладном коде следует ориентироваться прежде всего на числовой код, а не на текст `OK`, `Not Found` или `Created`.

## 5.2. Тело ответа

Тело ответа может содержать:

- HTML-документ;
- JSON;
- изображение;
- CSS;
- JavaScript;
- файл;
- сообщение об ошибке.

Например, backend API обычно возвращает JSON:

```
{
  "id": 42,
  "title": "Fullmetal Alchemist"
}
```

А сервер статического сайта может вернуть HTML:

```
<!doctype html>
<html>
  <head>
    <title>Каталог</title>
  </head>
  <body>
    <h1>Каталог аниме</h1>
  </body>
</html>
```

Формат тела определяется заголовком `Content-Type`:

```
Content-Type: application/json
Content-Type: text/html; charset=utf-8
Content-Type: text/css
Content-Type: image/png
```

## 5.3. Почему ответ `200` не всегда означает «всё хорошо»

Статус `200 OK` означает, что сервер успешно обработал запрос с точки зрения протокола, но это не гарантирует, что пользователь получил ожидаемые бизнес-данные.

Например, сервер может вернуть:

```
HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": false,
  "message": "Недостаточно средств"
}
```

Технически запрос обработан, но операция не была успешной с точки зрения предметной области. Поэтому API должен использовать статус-коды и формат ошибок последовательно, а frontend должен учитывать как HTTP-ошибки, так и ошибки бизнес-логики.

# 6. URL и его структура

## 6.1. Что такое URL

**URL**, или Uniform Resource Locator, — это адрес ресурса, позволяющий указать, где и каким способом его получить.

Пример:

```
https://example.com:443/catalog/anime/42?genre=fantasy#reviews
```

Разбор:

```
https://       схема
example.com   хост
:443          порт
/catalog      путь
/anime/42
?genre=...    query-параметры
#reviews      fragment
```

## 6.2. Схема

Схема определяет способ доступа к ресурсу:

```
https://
http://
```

В современных веб-приложениях практически всегда используется `https`, поскольку он обеспечивает шифрование соединения между клиентом и сервером посредством TLS.

Важно понимать, что HTTPS не меняет саму модель HTTP-запросов и HTTP-ответов. Он защищает канал передачи, но не исправляет ошибки в логике приложения и не делает автоматически безопасными плохо спроектированные endpoint’ы.

## 6.3. Хост

Хост определяет, с каким сетевым именем или адресом нужно связаться:

```
example.com
api.example.com
localhost
127.0.0.1
```

Доменное имя удобно человеку, а сетевое соединение в конечном счёте устанавливается с IP-адресом. Преобразование доменного имени в IP выполняет DNS.

## 6.4. Порт

Порт позволяет выбрать конкретный сетевой сервис на хосте:

```
https://example.com:443
http://localhost:3000
```

Если порт является стандартным для схемы, он обычно не указывается явно:

- HTTP обычно использует порт `80`;
- HTTPS обычно использует порт `443`.

При локальной разработке часто применяются порты вроде `3000`, `5173`, `8080`, поскольку на одной машине могут одновременно работать frontend, backend и другие сервисы.

## 6.5. Путь

Путь определяет положение ресурса в логической структуре приложения:

```
/catalog
/catalog/anime
/catalog/anime/42
```

Не следует автоматически считать, что путь соответствует физическому файлу. В старой модели URL мог указывать на файл `catalog/anime.html`, но современный backend чаще сопоставляет путь с маршрутом и программной логикой.

Например:

```
GET /api/anime/42
```

может привести к выполнению кода, который:

1. извлечёт идентификатор `42`;
2. запросит запись в базе данных;
3. проверит права доступа;
4. сформирует JSON;
5. вернёт ответ клиенту.

## 6.6. Query-параметры

Query-параметры передают дополнительные условия запроса:

```
/api/anime?genre=fantasy&page=2&limit=10
```

Их часто используют для:

- поиска;
- фильтрации;
- сортировки;
- пагинации;
- выбора формата;
- передачи необязательных параметров.

Query-параметры не должны использоваться для передачи секретов: URL может попадать в историю браузера, логи серверов, системы аналитики и заголовок Referer.

## 6.7. Fragment

Фрагмент начинается с символа `#`:

```
/catalog/anime/42#reviews
```

Он обычно обрабатывается браузером и не передаётся серверу в HTTP-запросе. Фрагменты применяются для перехода к части документа или для клиентской маршрутизации в некоторых SPA-приложениях.

Это важное различие:

```
Query:   ?page=2
Fragment: #reviews
```

Query видит сервер, а fragment в традиционном сценарии остаётся на стороне браузера.

## 6.8. Origin

Для безопасности браузер использует понятие **origin**, состоящее из:

```
scheme + host + port
```

Например:

```
https://example.com
```

и

```
http://example.com
```

имеют разные origin, поскольку отличаются схемой.

Также разными origin считаются:

```
https://example.com
https://api.example.com
https://example.com:8443
```

Различие origin имеет значение для CORS, cookies, локального хранилища и политики безопасности браузера.

# 7. Методы HTTP

## 7.1. Основные методы

|Метод|Назначение|Типичный пример|
|---|---|---|
|`GET`|Получение ресурса|Получить список аниме|
|`POST`|Создание ресурса или запуск операции|Создать новое аниме|
|`PUT`|Полная замена ресурса|Заменить все данные аниме|
|`PATCH`|Частичное изменение ресурса|Изменить только рейтинг|
|`DELETE`|Удаление ресурса|Удалить аниме|
|`HEAD`|Получение заголовков без тела|Проверить существование ресурса|
|`OPTIONS`|Узнать поддерживаемые возможности|Проверить CORS и методы|

## 7.2. GET

`GET` используется для получения ресурса:

```
GET /api/anime HTTP/1.1
```

Или конкретного объекта:

```
GET /api/anime/42 HTTP/1.1
```

Характерные свойства `GET`:

- данные обычно передаются через путь и query-параметры;
- запрос не должен изменять состояние сервера;
- ответ может кэшироваться;
- запрос можно безопасно повторить в обычной ситуации;
- тело запроса обычно не используется.

Запрос `GET` не должен применяться для операций вроде удаления или изменения данных:

```
GET /api/delete-user/42
```

Такой дизайн опасен, потому что GET-запросы могут автоматически выполняться браузером, поисковыми роботами, системами предварительной загрузки и кэширующими прокси.

## 7.3. POST

`POST` обычно используется для создания ресурса или передачи данных на обработку:

```
POST /api/anime HTTP/1.1
Content-Type: application/json

{
  "title": "Cowboy Bebop"
}
```

В отличие от `GET`, `POST` обычно содержит тело запроса и может изменять состояние сервера.

Примеры:

```
POST /api/users
POST /api/orders
POST /api/comments
POST /api/auth/login
```

Один и тот же POST-запрос, повторённый несколько раз, потенциально может создать несколько ресурсов. Поэтому операции создания требуют внимательного отношения к повторной отправке, сетевым сбоям и идемпотентности.

## 7.4. PUT

`PUT` применяется для полной замены ресурса:

```
PUT /api/anime/42
Content-Type: application/json

{
  "title": "Fullmetal Alchemist: Brotherhood",
  "year": 2009,
  "genre": "fantasy"
}
```

Идея состоит в том, что клиент передаёт новое полное представление ресурса. Если поле должно сохраниться, оно обычно также включается в тело запроса.

## 7.5. PATCH

`PATCH` предназначен для частичного изменения:

```
PATCH /api/anime/42
Content-Type: application/json

{
  "rating": 9.5
}
```

Здесь клиент не обязан передавать все поля объекта: он сообщает только изменения.

На практике различие между `PUT` и `PATCH` иногда размывается конкретным API, однако в учебном курсе важно закрепить концептуальное различие:

- `PUT` — заменить представление целиком;
- `PATCH` — изменить часть представления.

## 7.6. DELETE

`DELETE` используется для удаления ресурса:

```
DELETE /api/anime/42 HTTP/1.1
```

Успешный ответ может иметь статус:

```
204 No Content
```

В таком случае сервер сообщает, что операция выполнена, но не возвращает тело ответа.

## 7.7. Идемпотентность

Метод называется идемпотентным, если многократное выполнение одного и того же запроса приводит к тому же результату на сервере, что и однократное выполнение, хотя ответы могут отличаться.

В учебном приближении:

- `GET` — безопасный и идемпотентный;
- `PUT` — обычно идемпотентный;
- `DELETE` — обычно идемпотентный;
- `POST` — обычно неидемпотентный;
- `PATCH` зависит от конкретной операции.

Например, повторная команда:

```
PUT /api/users/42
```

с одним и тем же полным телом обычно оставляет ресурс в том же состоянии.

А два одинаковых запроса:

```
POST /api/orders
```

могут создать два заказа. Это не означает, что POST «нельзя повторять», но сервер должен учитывать возможные повторы, если операция финансовая или критически важная.

## 7.8. Метод не заменяет права доступа

Использование `DELETE` не означает, что любой клиент автоматически имеет право удалить ресурс. Метод описывает намерение, а сервер обязан дополнительно проверить:

- аутентифицирован ли пользователь;
- имеет ли он необходимые права;
- существует ли ресурс;
- допустима ли операция в текущем состоянии;
- корректны ли входные данные.

# 8. HTTP-статус-коды

## 8.1. Классы статусов

Статус-коды делятся на пять классов:

|Класс|Диапазон|Смысл|
|---|---|---|
|`1xx`|100–199|Информационные сообщения|
|`2xx`|200–299|Успешное выполнение|
|`3xx`|300–399|Перенаправление или дополнительные действия|
|`4xx`|400–499|Ошибка запроса клиента|
|`5xx`|500–599|Ошибка сервера|

Класс определяется первой цифрой. Поэтому `404` и `401` относятся к ошибкам клиента, а `500` и `503` — к проблемам на стороне сервера.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)]

## 8.2. Наиболее важные статусы

### `200 OK`

Запрос успешно обработан, и ответ содержит результат:

```
HTTP/1.1 200 OK
```

Часто используется для успешного `GET`, а также для операций, в которых сервер возвращает данные после изменения.

### `201 Created`

Ресурс успешно создан:

```
HTTP/1.1 201 Created
Location: /api/anime/42
```

Для создания ресурса полезно вернуть `201` и, при необходимости, указать адрес нового ресурса в заголовке `Location`.

### `204 No Content`

Операция успешна, но тело ответа отсутствует:

```
HTTP/1.1 204 No Content
```

Часто применяется после успешного удаления или изменения, когда клиенту не нужно возвращать объект.

### `301 Moved Permanently`

Ресурс постоянно перемещён на другой адрес. Браузеры и поисковые системы могут запоминать такое перенаправление.

### `302 Found`

Временное перенаправление. Сервер сообщает клиенту, что сейчас ресурс доступен по другому адресу.

### `304 Not Modified`

Ресурс не изменился с момента предыдущего запроса, поэтому клиент может использовать кэшированную копию.

### `400 Bad Request`

Запрос имеет некорректный формат или не может быть обработан:

- повреждённый JSON;
- отсутствует обязательное поле;
- некорректный параметр;
- нарушена структура запроса.

### `401 Unauthorized`

В контексте веб-приложений обычно означает, что клиент не прошёл аутентификацию:

- токен отсутствует;
- токен просрочен;
- учётные данные неверны.

Название статуса может вводить в заблуждение: речь чаще идёт не о недостатке прав, а об отсутствии подтверждённой личности.

### `403 Forbidden`

Сервер понял запрос и личность клиента, но запрещает выполнение операции:

- пользователь не имеет нужной роли;
- ресурс принадлежит другому пользователю;
- доступ запрещён политикой приложения.

Упрощённое различие:

```
401 — «Кто вы?»
403 — «Я знаю, кто вы, но вам нельзя»
```

### `404 Not Found`

Сервер не нашёл ресурс по указанному адресу. Это может означать:

- неправильный URL;
- отсутствующий объект;
- удалённую запись;
- намеренно скрываемый ресурс.

### `405 Method Not Allowed`

Маршрут существует, но данный HTTP-метод для него не поддерживается:

```
GET /api/anime/42
```

может существовать, а:

```
PATCH /api/anime/42
```

может быть запрещён.

### `409 Conflict`

Запрос конфликтует с текущим состоянием ресурса:

- попытка зарегистрировать уже существующий email;
- конфликт версий;
- нарушение уникального ограничения;
- попытка выполнить несовместимую операцию.

### `422 Unprocessable Content`

Структура запроса понятна, но содержимое не проходит бизнес-валидацию:

```
{
  "email": "invalid",
  "age": -5
}
```

Сервер смог разобрать запрос, но не может принять такие данные.

### `429 Too Many Requests`

Клиент отправил слишком много запросов за определённый период. Этот статус используется механизмами rate limiting.

### `500 Internal Server Error`

На сервере произошла непредвиденная ошибка. Клиент обычно не может исправить её изменением того же самого запроса.

### `502 Bad Gateway`

Прокси или шлюз получил некорректный ответ от вышестоящего сервера.

### `503 Service Unavailable`

Сервис временно недоступен, например из-за перегрузки, технических работ или недоступности зависимости.

### `504 Gateway Timeout`

Промежуточный сервер не дождался ответа от другого сервера.

## 8.3. Ошибка клиента и ошибка сервера

Важное правило:

> Статус `4xx` обычно означает, что запрос необходимо изменить, а статус `5xx` — что проблема возникла при обработке корректного запроса на стороне сервера или его инфраструктуры.

Например:

```
400 — клиент отправил некорректные данные.
401 — клиент не подтвердил личность.
403 — клиенту запрещена операция.
404 — ресурс не найден.
500 — сервер столкнулся с внутренней ошибкой.
```

При этом нельзя бездумно возвращать `500` на любую проблему. Если пользователь отправил неверные данные, это не внутренняя ошибка сервера, а ожидаемая ситуация валидации, которую следует описать статусом класса `4xx`.

# 9. Frontend, backend и база данных

## 9.1. Frontend

**Frontend** — часть веб-приложения, которая выполняется на стороне клиента и отвечает за взаимодействие с пользователем.

Frontend включает:

- HTML-структуру;
- CSS-оформление;
- JavaScript-логику;
- управление состоянием интерфейса;
- обработку событий;
- отправку запросов к API;
- отображение данных;
- клиентскую валидацию;
- работу с браузерными API.

Frontend может получить данные:

```
GET /api/anime
```

затем преобразовать JSON в карточки и вставить их в DOM.

Однако frontend нельзя считать доверенной средой: пользователь может изменить JavaScript, отправить запрос вручную или обойти интерфейс. Поэтому важные проверки должны выполняться на backend.

## 9.2. Backend

**Backend** — серверная часть приложения, которая принимает запросы, выполняет бизнес-логику и формирует ответы.

Backend отвечает за:

- маршрутизацию;
- аутентификацию;
- авторизацию;
- валидацию данных;
- работу с базой;
- правила предметной области;
- интеграцию с внешними сервисами;
- обработку ошибок;
- логирование;
- формирование API-ответов.

Например, при создании заказа backend должен проверить не только наличие полей, но и:

- существует ли товар;
- доступно ли нужное количество;
- может ли пользователь оформить заказ;
- не изменилась ли цена;
- допустим ли текущий статус заказа.

## 9.3. База данных

**База данных** предназначена для долговременного хранения и поиска информации.

В учебном проекте она может хранить:

```
Пользователи
- id
- email
- password_hash

Аниме
- id
- title
- year
- description

Оценки
- id
- user_id
- anime_id
- value
```

База данных не должна напрямую открываться браузеру. Обычно frontend взаимодействует с backend, а backend уже обращается к базе:

```
Frontend
   ↓ HTTP
Backend
   ↓ SQL или ORM
Database
```

Такой подход позволяет централизованно контролировать:

- безопасность;
- права доступа;
- структуру данных;
- транзакции;
- бизнес-правила;
- формат ответов.

## 9.4. Почему нельзя передавать frontend прямой доступ к базе

Если браузер получит прямые учётные данные базы, любой пользователь сможет попытаться:

- прочитать чужие данные;
- изменить записи;
- удалить таблицы;
- обойти бизнес-ограничения;
- выполнить произвольные запросы.

Даже если использовать специальный промежуточный сервис, доступ должен предоставляться через контролируемый API, а не через секреты базы данных, встроенные в клиентский код.

# 10. Как браузер получает страницу

Рассмотрим переход пользователя по адресу:

```
https://example.com/catalog
```

## Шаг 1. Ввод адреса

Пользователь вводит URL или нажимает ссылку. Браузер определяет, что необходимо загрузить ресурс по схеме HTTPS.

## Шаг 2. Определение адреса сервера

Если используется доменное имя, браузеру необходимо узнать соответствующий IP-адрес. Для этого используется DNS. Результат может быть взят из кэша браузера, операционной системы или промежуточного DNS-сервера.

## Шаг 3. Установление соединения

Браузер устанавливает сетевое соединение с сервером. Для HTTPS дополнительно выполняется TLS-рукопожатие, в ходе которого стороны согласуют параметры шифрования и сервер подтверждает свою идентичность сертификатом.

На этом этапе не следует смешивать уровни абстракции:

- DNS отвечает за поиск адреса;
- TCP или QUIC обеспечивают транспорт;
- TLS защищает соединение;
- HTTP описывает запросы и ответы приложения.

## Шаг 4. Отправка HTTP-запроса

Браузер отправляет запрос:

```
GET /catalog HTTP/1.1
Host: example.com
Accept: text/html
Accept-Language: ru
User-Agent: Mozilla/5.0
```

Сервер получает запрос, определяет маршрут и выбирает обработчик.

## Шаг 5. Формирование HTTP-ответа

Сервер может:

- найти готовый HTML-файл;
- сгенерировать HTML динамически;
- обратиться к базе данных;
- вызвать другой сервис;
- проверить cookies;
- проверить права доступа;
- вернуть ошибку или перенаправление.

Пример успешного ответа:

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!doctype html>
<html>
  ...
</html>
```

## Шаг 6. Разбор HTML

Браузер получает байты, декодирует их с учётом кодировки и разбирает HTML. В результате формируется **DOM**, или Document Object Model, — объектная структура документа в памяти.

Для такого HTML:

```
<p>
  Используем
  <span>HTML</span>
  <span>CSS</span>
</p>
```

DOM концептуально будет выглядеть так:

```
P
├── текст «Используем»
├── SPAN
│   └── текст «HTML»
└── SPAN
    └── текст «CSS»
```

DOM — это не исходный текст HTML и не готовая картинка, а структурированное представление документа, с которым затем может работать JavaScript.

## Шаг 7. Дополнительные запросы

Обрабатывая HTML, браузер обнаруживает ссылки на внешние ресурсы:

```
<link rel="stylesheet" href="/styles/main.css">
<script src="/scripts/app.js"></script>
<img src="/images/logo.png" alt="Логотип">
```

После этого он выполняет дополнительные запросы:

```
GET /styles/main.css
GET /scripts/app.js
GET /images/logo.png
```

Именно поэтому одна веб-страница обычно соответствует не одному HTTP-запросу, а множеству запросов к различным ресурсам. Браузер собирает эти ресурсы и объединяет их в единое пользовательское представление.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_browsers_load_websites)]

## Шаг 8. Построение CSSOM

CSS разбирается браузером в структуру, которую называют CSSOM — CSS Object Model. Затем правила сопоставляются с узлами DOM.

Например:

```
.card {
  color: navy;
}
```

Браузер определяет, какие элементы относятся к классу `card`, какие свойства для них действуют и какие правила имеют приоритет.

## Шаг 9. Построение render tree

На основе DOM и CSSOM браузер формирует render tree — дерево визуально отображаемых объектов. В него не обязательно попадают все DOM-узлы: например, элемент с `display: none` не занимает место и не отображается.

Render tree содержит информацию, необходимую для последующего расчёта внешнего вида страницы.

## Шаг 10. Layout

На этапе layout браузер рассчитывает геометрию:

- ширину и высоту элементов;
- их координаты;
- расположение в потоке;
- размеры текста;
- положение изображений;
- переносы строк.

Если изменяется размер окна браузера, layout может быть выполнен заново.

## Шаг 11. Paint

На этапе paint браузер рисует рассчитанные элементы:

- фон;
- границы;
- текст;
- изображения;
- тени;
- эффекты.

После этого результат преобразуется в пиксели и выводится на экран. Современные браузеры могут дополнительно распределять отдельные слои и операции между CPU и GPU.

## Шаг 12. Выполнение JavaScript

JavaScript может:

- изменить DOM;
- добавить или удалить элементы;
- изменить классы;
- запросить данные через API;
- изменить стили;
- зарегистрировать обработчики событий;
- вызвать повторный layout или paint.

Поэтому отображение страницы не всегда является одноразовой процедурой. После первоначального рендера пользовательские действия и сетевые ответы могут запускать новые циклы обновления интерфейса.

MDN описывает этот путь через основные структуры DOM, CSSOM, render tree, layout и paint, подчёркивая, что браузер превращает HTML, CSS и JavaScript в пиксели на экране.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path)]

# 11. Важное уточнение о порядке загрузки

Упрощённая схема:

```
HTML → DOM
CSS → CSSOM
DOM + CSSOM → Render Tree
Render Tree → Layout
Layout → Paint
JavaScript → изменение DOM и поведения
```

не означает, что браузер всегда выполняет абсолютно все этапы строго один раз и в неизменном порядке.

На реальное поведение влияют:

- тип подключения скрипта;
- атрибуты `defer` и `async`;
- блокирующие CSS-ресурсы;
- размер документов;
- кэш;
- приоритеты загрузки;
- браузерный движок;
- динамические изменения DOM;
- доступность ресурсов;
- сетевые задержки.

Поэтому студенту полезно усвоить не механическую цепочку, а причинно-следственную связь:

> HTML задаёт структуру, CSS задаёт визуальные правила, JavaScript задаёт поведение, а браузер объединяет результаты их обработки в интерактивное представление.

# 12. Структура учебного проекта

Для курса предлагается использовать единый клиент-серверный проект, который будет постепенно развиваться на лабораторных работах.

## 12.1. Базовая структура

```
web-course-project/
├── frontend/
│   ├── index.html
│   ├── styles/

# 14. Типичные неправильные представления

## Ошибка 1. «Сайт — это один HTML-файл»

HTML — только один из ресурсов и языков веб-приложения. Полноценный проект может включать CSS, JavaScript, изображения, API, базу данных, авторизацию и серверную логику.

## Ошибка 2. «Браузер отправляет запрос только при открытии страницы»

После получения HTML браузер отправляет дополнительные запросы за CSS, JavaScript, изображениями, шрифтами и данными API.

## Ошибка 3. «Frontend отвечает за безопасность»

Frontend может улучшить пользовательский опыт, но не является доверенной средой. Любой пользователь способен изменить код или сформировать запрос вручную, поэтому backend обязан повторно проверять права и данные.

## Ошибка 4. «404 означает, что сломался интернет»

`404` означает, что сервер не нашёл ресурс по данному адресу. Сетевое соединение при этом могло работать полностью корректно.

## Ошибка 5. «500 означает ошибку пользователя»

`500` обычно указывает на внутреннюю проблему сервера. Ошибочные пользовательские данные следует отражать статусами класса `4xx`, если сервер способен корректно их распознать.

## Ошибка 6. «URL и endpoint — одно и то же»

URL — адрес ресурса в общем смысле, а endpoint — конкретная точка взаимодействия API, обычно описываемая комбинацией метода и пути:

```
GET /api/anime
POST /api/anime
GET /api/anime/:id
```

Один и тот же путь с разными методами может представлять разные операции.

## Ошибка 7. «HTTPS делает приложение безопасным»

HTTPS защищает передаваемые данные от перехвата на уровне соединения, но не предотвращает:

- неправильную авторизацию;
- SQL-инъекции;
- утечку секретов;
- ошибки бизнес-логики;
- XSS;
- небезопасное хранение токенов.

# Часть 2. HTML: структура и смысл веб-документа

## Цели части

Главная идея этой части:

> HTML описывает не внешний вид страницы, а структуру и смысл её содержимого.

Если CSS отвечает на вопрос «как это выглядит», а JavaScript — «как это ведёт себя», то HTML отвечает на более фундаментальный вопрос: **что именно находится на странице и какую роль выполняет каждый элемент**.

HTML является структурированным языком разметки: элементы сообщают браузеру и вспомогательным технологиям, является ли фрагмент заголовком, ссылкой, формой, изображением, навигацией или самостоятельной единицей контента. Семантика HTML важна не только для читаемости кода, но и для доступности, поисковой индексации и встроенного поведения браузера.[[html.spec.whatwg](https://html.spec.whatwg.org/multipage/dom.html)][[developer.mozilla](https://developer.mozilla.org/en-US/curriculum/core/semantic-html/)]

---

# 1. HTML как язык разметки

## 1.1. HTML не является языком программирования

HTML не содержит обычной для языков программирования логики: условий, циклов, функций, переменных, алгоритмов. Он описывает документ с помощью элементов и атрибутов.

Например:

```
<h1>Каталог аниме</h1>
<p>Подборка сериалов и полнометражных фильмов.</p>
```

Здесь HTML сообщает:

- первая строка является главным заголовком;
- вторая строка является абзацем.

Браузер затем самостоятельно решает, как отобразить эти элементы по умолчанию, но это отображение — лишь визуальное следствие их смысла. Заголовок важен не потому, что браузер обычно делает его крупнее, а потому, что он обозначает тему документа или его раздела.

## 1.2. Элемент, тег и атрибут

В HTML нужно различать три понятия.
### Тег

Тег — это синтаксическая запись имени элемента:

```
<p>
</p>
```

### Элемент

Элемент — это сама конструкция, состоящая из открывающего тега, содержимого и закрывающего тега:

```
<p>Текст абзаца</p>
```

### Атрибут

Атрибут добавляет элементу дополнительную информацию:

```
<a href="/catalog">Перейти в каталог</a>
```

Здесь:

- `a` — элемент ссылки;
- `href` — атрибут;
- `"/catalog"` — значение атрибута;
- `Перейти в каталог` — содержимое ссылки.

В общем виде элемент можно представить так:

```
<имя-элемента атрибут="значение">
  содержимое
</имя-элемента>
```

Однако не все элементы имеют закрывающий тег. Например:

```
<img src="/images/logo.png" alt="Логотип">
<input type="email" name="email">
<meta charset="UTF-8">
```

Такие элементы не содержат вложенного текстового содержимого и называются пустыми, или void elements.

## 1.3. Вложенность элементов

HTML образует древовидную структуру. Элементы могут быть вложены друг в друга:

```
<article>
  <h2>Fullmetal Alchemist</h2>
  <p>История братьев Элриков.</p>
</article>
```

Здесь:

- `article` является родительским элементом;
- `h2` и `p` являются его дочерними элементами;
- текст внутри `h2` и `p` является текстовым содержимым.

Корректная вложенность означает, что элементы закрываются в обратном порядке открытия:

```
<p>
  Текст с <strong>важным фрагментом</strong>.
</p>
```

Некорректный вариант:

```
<p>
  Текст с <strong>важным фрагментом.
</p>
</strong>
```

Браузер в большинстве случаев попытается исправить ошибочную разметку, однако полагаться на автоматическое исправление нельзя: разные браузеры и инструменты могут построить DOM не совсем одинаково, а отладка такого кода становится существенно сложнее.

# 2. Структура HTML-документа

## 2.1. Минимальный документ

Базовый HTML-документ обычно выглядит так:

```
<!doctype html>
<html lang="ru">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Каталог аниме</title>
  </head>
  <body>
    <h1>Каталог аниме</h1>
    <p>Добро пожаловать в каталог.</p>
  </body>
</html>
```

Рассмотрим его сверху вниз.

## 2.2. `<!doctype html>`

```
<!doctype html>
```

Эта строка сообщает браузеру, что документ следует интерпретировать в современном режиме HTML.

Исторически HTML имел длинные объявления DOCTYPE, связанные с конкретными версиями и типами документа. Современная запись намеренно короткая: разработчику не требуется указывать сложную строку для перехода к стандартному режиму обработки.

Если DOCTYPE отсутствует или записан некорректно, браузер может включить quirks mode — режим совместимости с устаревшими особенностями. Это способно повлиять на расчёт размеров и отображение CSS, поэтому DOCTYPE должен присутствовать в начале документа.

## 2.3. Элемент `html`

```
<html lang="ru">
```

Элемент `html` является корневым элементом документа: все остальные элементы находятся внутри него.

Атрибут `lang` сообщает язык содержимого:

```
<html lang="ru">
```

Для английского документа:

```
<html lang="en">
```

Язык важен для:

- программ чтения с экрана;
- автоматического выбора произношения;
- проверки орфографии;
- поисковых систем;
- корректной обработки текста и переносов.

Указывать `lang` следует не только ради формального соответствия стандарту: это реальная часть описания документа.

## 2.4. Элемент `head`

```
<head>
  <meta charset="UTF-8">
  <title>Каталог аниме</title>
</head>
```

`head` содержит метаданные и ресурсы, необходимые для обработки документа, но обычно не отображаемые как основное содержимое страницы.

В `head` могут находиться:

- кодировка;
- заголовок вкладки;
- viewport;
- ссылки на CSS;
- favicon;
- метаописание;
- подключения шрифтов;
- настройки кэширования;
- внешние скрипты.

Пример:

```
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <meta
    name="description"
    content="Каталог аниме с описаниями и рейтингами"
  >
  <title>Каталог аниме</title>
  <link rel="stylesheet" href="/styles/main.css">
</head>
```

## 2.5. Кодировка

```
<meta charset="UTF-8">
```

Атрибут `charset` сообщает браузеру, как интерпретировать байты документа как символы. `UTF-8` поддерживает русский язык, латиницу, математические символы, эмодзи и множество других письменностей.

Если кодировка страницы и кодировка, в которой файл сохранён, не совпадают, пользователь может увидеть нечитаемый текст:

```
ÐšÐ°Ñ‚Ð°Ð»Ð¾Ð³
```

Поэтому кодировку следует объявлять как можно раньше внутри `head`.

## 2.6. Viewport

```
<meta name="viewport" content="width=device-width, initial-scale=1">
```

Этот метатег особенно важен для мобильных устройств.

Его смысл:

- ширина страницы должна соответствовать ширине viewport устройства;
- начальный масштаб равен единице.

Без него мобильный браузер может использовать виртуальную широкую область просмотра и уменьшить страницу, из-за чего адаптивная вёрстка будет работать непредсказуемо.

## 2.7. Элемент `title`

```
<title>Каталог аниме</title>
```

`title` задаёт название документа. Оно отображается:

- в заголовке вкладки;
- в списке истории браузера;
- в закладках;
- в результатах поиска в качестве одного из источников названия;
- во вспомогательных технологиях.

`title` не следует путать с заголовком `h1`. `title` описывает документ на уровне браузера, а `h1` является видимым заголовком основного содержимого.

## 2.8. Элемент `body`

```
<body>
  <h1>Каталог аниме</h1>
</body>
```

`body` содержит содержимое страницы:

- текст;
- заголовки;
- изображения;
- ссылки;
- формы;
- таблицы;
- видео;
- интерактивные элементы;
- структурные секции.

В документе обычно должен быть один `head` и один `body`, а основное отображаемое содержимое располагается внутри `body`.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements)]

# 3. Заголовки и абзацы

## 3.1. Заголовки `h1`–`h6`

HTML предоставляет шесть уровней заголовков:

```
<h1>Каталог аниме</h1>
<h2>Популярные сериалы</h2>
<h3>Фэнтези</h3>
<h3>Фантастика</h3>
<h2>Новые поступления</h2>
```

Уровень заголовка отражает структуру документа:

- `h1` — основная тема страницы;
- `h2` — крупный раздел;
- `h3` — подраздел внутри `h2`;
- `h4`–`h6` — последующие уровни вложенности.

Заголовок — это не просто крупный текст. Если требуется визуально сделать обычный текст крупнее, для этого используется CSS, а не выбор заголовка с подходящим размером.

Неправильно:

```
<h1>Каталог</h1>
<h4>Популярные аниме</h4>
```

если между ними отсутствуют логические уровни `h2` и `h3`.

Лучше:

```
<h1>Каталог</h1>
<h2>Популярные аниме</h2>
```

## 3.2. Один ли должен быть `h1`

В учебной модели удобно рекомендовать один основной `h1` на страницу. Это помогает поддерживать ясную структуру документа.

Однако более важен не механический подсчёт заголовков, а корректная иерархия. В сложных приложениях отдельные представления могут иметь собственный `h1`, если они являются самостоятельными документами или экранами.

Практическое правило:

> На каждой странице должен быть понятный главный заголовок, а дальнейшие разделы должны выстраиваться без необоснованных скачков уровней.

## 3.3. Абзацы

```
<p>
  Каталог содержит описания, рейтинги и жанры популярных произведений.
</p>
```

`p` обозначает отдельный абзац. Не следует использовать несколько переносов строк внутри обычного HTML-текста для имитации абзацев:

```
Каталог аниме.<br><br>
Здесь собраны популярные произведения.
```

Такой код смешивает структуру документа с визуальным форматированием. Для двух абзацев следует использовать два элемента `p`:

```
<p>Каталог аниме.</p>
<p>Здесь собраны популярные произведения.</p>
```

Перенос `br` предназначен для ситуаций, когда перенос является частью самого содержимого, например в адресе или стихотворении:

```
<p>
  г. Белорецк<br>
  Республика Башкортостан
</p>
```

## 4.1. Маркированный список

```
<ul>
  <li>Фэнтези</li>
  <li>Фантастика</li>
  <li>Драма</li>
</ul>
```

`ul` означает unordered list — неупорядоченный список, а `li` — его элемент.

Порядок элементов здесь не имеет принципиального значения.

## 4.2. Нумерованный список

```
<ol>
  <li>Выбрать произведение.</li>
  <li>Открыть страницу деталей.</li>
  <li>Поставить оценку.</li>
</ol>
```

`ol` используется, когда порядок имеет смысл:

- инструкция;
- алгоритм действий;
- рейтинг;
- последовательность этапов;
- список шагов.

## 4.3. Вложенные списки

```
<ul>
  <li>
    Фэнтези
    <ul>
      <li>Алхимия</li>
      <li>Магия</li>
    </ul>
  </li>
  <li>Фантастика</li>
</ul>
```

Вложенный список должен находиться внутри `li`, к которому он относится. Нельзя помещать `ul` непосредственно внутрь другого `ul`, минуя `li`.

## 4.4. Список определений

Для терминов и их описаний существует `dl`:

```
<dl>
  <dt>Frontend</dt>
  <dd>Клиентская часть веб-приложения.</dd>

  <dt>Backend</dt>
  <dd>Серверная часть веб-приложения.</dd>
</dl>
```

Здесь:

- `dl` — список определений;
- `dt` — термин;
- `dd` — его описание.

## 4.5. Типичная ошибка со списками

Неправильно использовать обычный текст и символы вместо списка:

```
<p>• HTML</p>
<p>• CSS</p>
<p>• JavaScript</p>
```

Такой вариант визуально может выглядеть похожим на список, но браузер и вспомогательные технологии не получат информацию о количестве элементов и структуре списка.

Правильно:

```
<ul>
  <li>HTML</li>
  <li>CSS</li>
  <li>JavaScript</li>
</ul>
```

# 5. Ссылки

## 5.1. Элемент `a`

Ссылка создаётся элементом `a` с атрибутом `href`:

```
<a href="/catalog">Открыть каталог</a>
```

Ссылка является интерактивным элементом, который позволяет перейти к другому ресурсу, документу, фрагменту текущей страницы или инициировать специальное действие.

## 5.2. Виды адресов

Абсолютный URL:

```
<a href="https://example.com/catalog">
  Внешний каталог
</a>
```

Корневой относительный путь:

```
<a href="/catalog">Каталог</a>
```

Относительный путь:

```
<a href="./details.html">Подробнее</a>
```

Переход к фрагменту страницы:

```
<a href="#reviews">К отзывам</a>

<section id="reviews">
  <h2>Отзывы</h2>
</section>
```

## 5.3. Текст ссылки

Текст ссылки должен объяснять, куда она ведёт:

```
<a href="/anime/42">Открыть страницу Fullmetal Alchemist</a>
```

Неудачный вариант:

```
<a href="/anime/42">Нажмите здесь</a>
```

Если на странице несколько ссылок с текстом «Подробнее», пользователь, который перемещается с помощью клавиатуры или программы чтения с экрана, не получает достаточно информации о назначении каждой ссылки.

Особенно плохо:

```
<a href="/anime/42">Подробнее</a>
<a href="/anime/43">Подробнее</a>
<a href="/anime/44">Подробнее</a>
```

Лучше:

```
<a href="/anime/42">
  Подробнее о Fullmetal Alchemist
</a>
<a href="/anime/43">
  Подробнее о Cowboy Bebop
</a>
<a href="/anime/44">
  Подробнее о Death Note
</a>
```

## 5.4. Ссылка и кнопка

Это одно из принципиальных различий HTML.

**Ссылка** ведёт к ресурсу или изменяет адрес:

```
<a href="/profile">Профиль</a>
```

**Кнопка** выполняет действие на текущей странице:

```
<button type="button">Открыть фильтры</button>
```

Неправильно использовать ссылку с `href="#"` вместо кнопки:

```
<a href="#" onclick="openFilters()">Открыть фильтры</a>
```

Если элемент открывает модальное окно, изменяет состояние интерфейса, запускает фильтрацию или отправляет локальную операцию, семантически правильнее использовать `button`.

Различие важно потому, что браузер, клавиатура и вспомогательные технологии уже знают стандартное поведение ссылок и кнопок.

## 5.5. Открытие новой вкладки

```
<a
  href="https://example.com"
  target="_blank"
  rel="noopener noreferrer"
>
  Открыть внешний ресурс
</a>
```

`target="_blank"` открывает ресурс в новой вкладке или окне. `rel="noopener"` предотвращает доступ новой страницы к объекту `window.opener`, а `noreferrer` дополнительно ограничивает передачу источника перехода.

Внешний переход желательно обозначать понятным текстом, если открытие новой вкладки может быть неожиданным для пользователя.

# 6. Изображения

## 6.1. Элемент `img`

Изображение добавляется элементом `img`:

```
<img
  src="/images/fullmetal-alchemist.jpg"
  alt="Обложка аниме Fullmetal Alchemist"
>
```

Основные атрибуты:

- `src` — адрес изображения;
- `alt` — текстовая альтернатива;
- `width` — ширина;
- `height` — высота;
- `loading` — стратегия загрузки;
- `srcset` и `sizes` — варианты для разных экранов.

## 6.2. Атрибут `alt`

`alt` необходим для того, чтобы смысл изображения был доступен пользователю, который:

- не видит изображение;
- использует программу чтения с экрана;
- находится при медленном соединении;
- столкнулся с ошибкой загрузки ресурса.

Хороший `alt` описывает смысл изображения кратко:

```
<img
  src="/images/edward.jpg"
  alt="Эдвард Элрик в красном плаще"
>
```

Плохой вариант:

```
<img src="/images/edward.jpg" alt="картинка">
```

Ещё хуже:

```
<img src="/images/edward.jpg" alt="image12345">
```

Если изображение декоративное и не передаёт самостоятельной информации, используется пустой `alt`:

```
<img src="/images/decorative-line.svg" alt="">
```

Пустой `alt` сообщает вспомогательной технологии, что изображение не нужно объявлять пользователю. Полностью пропускать `alt` обычно не следует: отсутствие атрибута и пустое значение имеют различный смысл. HTML Standard указывает, что альтернативный текст должен быть подходящим представлением смысла изображения, а MDN подчёркивает необходимость учитывать, какую информацию изображение передаёт в контексте страницы.[[html.spec.whatwg](https://html.spec.whatwg.org/multipage/images.html)][[developer.mozilla](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML)]

## 6.3. Изображение как ссылка

Если изображение является ссылкой, текстовая альтернатива должна объяснять назначение ссылки:

```
<a href="/anime/42">
  <img
    src="/images/fullmetal-alchemist.jpg"
    alt="Открыть страницу Fullmetal Alchemist"
  >
</a>
```

Если рядом есть полноценный текст ссылки:

```
<a href="/anime/42">
  <img src="/images/fullmetal-alchemist.jpg" alt="">
  <span>Fullmetal Alchemist</span>
</a>
```

Здесь `alt=""` предотвращает дублирование названия, поскольку оно уже представлено текстом ссылки.

## 6.4. Ширина и высота изображения

Желательно указывать размеры изображения:

```
<img
  src="/images/poster.jpg"
  alt="Постер фильма"
  width="300"
  height="450"
>
```

Это позволяет браузеру заранее зарезервировать место и уменьшить скачки интерфейса во время загрузки изображения.

Визуальные размеры затем могут регулироваться CSS:

```
.poster {
  width: 100%;
  height: auto;
}
```

HTML-атрибуты `width` и `height` описывают исходные пропорции и резервируемую область, а CSS управляет фактическим отображением.

## 6.5. Ленивое изображение

Для второстепенных изображений можно использовать:

```
<img
  src="/images/poster.jpg"
  alt="Постер фильма"
  loading="lazy"
>
```

Однако основное изображение в верхней видимой части страницы не следует бездумно делать ленивым: браузер должен получить критически важный контент как можно раньше.

## 6.6. `figure` и `figcaption`

Если изображение имеет подпись, можно использовать:

```
<figure>
  <img
    src="/images/alchemy-circle.jpg"
    alt="Алхимический круг на каменном полу"
  >
  <figcaption>
    Иллюстрация алхимического круга из учебного проекта.
  </figcaption>
</figure>
```

`figure` обозначает самостоятельный фрагмент контента, а `figcaption` — его подпись.

# 7. Формы

## 7.1. Назначение формы

Форма собирает данные пользователя и передаёт их на обработку:

```
<form action="/api/anime" method="post">
  ...
</form>
```

Форма может использоваться для:

- регистрации;
- входа;
- поиска;
- фильтрации;
- добавления товара;
- оформления заказа;
- отправки комментария;
- загрузки файла.

## 7.2. Атрибуты `action` и `method`

```
<form action="/api/anime" method="post">
```

`action` указывает адрес обработчика, а `method` — HTTP-метод.

Наиболее распространённые методы HTML-формы:

- `get`;
- `post`.

Пример формы поиска:

```
<form action="/catalog" method="get">
  <label for="search">Поиск</label>
  <input id="search" name="q" type="search">
  <button type="submit">Найти</button>
</form>
```

После отправки браузер может сформировать адрес:

```
/catalog?q=fullmetal
```

Пример формы создания ресурса:

```
<form action="/api/anime" method="post">
  <label for="title">Название</label>
  <input id="title" name="title" type="text" required>

  <button type="submit">Добавить</button>
</form>
```

## 7.3. Связь `label` и `input`

Корректная форма должна связывать подпись и поле:

```
<label for="email">Электронная почта</label>
<input id="email" name="email" type="email">
```

Связь устанавливается так:

```
label[for] → input[id]
```

Преимущества:

- пользователь понимает назначение поля;
- нажатие на подпись переводит фокус в input;
- программа чтения с экрана сообщает подпись вместе с полем;
- область взаимодействия становится удобнее.

Допустим также вариант с вложенным полем:

```
<label>
  Электронная почта
  <input name="email" type="email">
</label>
```

На практике явная связь через `for` и `id` часто лучше читается и проще поддерживается.

## 7.4. Атрибут `name`

```
<input
  id="title"
  name="title"
  type="text"
>
```

`name` определяет имя поля при отправке формы. `id` и `name` решают разные задачи:

- `id` идентифицирует элемент в документе и связывает его с `label`;
- `name` определяет ключ, под которым значение попадёт в отправляемые данные.

Если у input отсутствует `name`, его значение обычно не будет включено в данные стандартной отправки формы.

## 7.5. Типы полей

HTML предоставляет типы, соответствующие характеру данных:

```
<input type="text">
<input type="email">
<input type="password">
<input type="number">
<input type="tel">
<input type="url">
<input type="date">
<input type="search">
<input type="checkbox">
<input type="radio">
<input type="file">
```

Выбор правильного типа даёт встроенные преимущества:

- браузер может выполнить базовую проверку;
- на мобильной клавиатуре появится подходящая раскладка;
- вспомогательные технологии получат более точную информацию;
- браузер может предложить автозаполнение;
- пользователю будет понятнее назначение поля.

Например:

```
<label for="rating">Рейтинг</label>
<input
  id="rating"
  name="rating"
  type="number"
  min="0"
  max="10"
  step="0.1"
>
```

## 7.6. Обязательные поля

```
<input
  id="title"
  name="title"
  type="text"
  required
>
```

Атрибут `required` включает встроенную проверку обязательности. Но встроенная валидация не заменяет серверную: пользователь может отключить JavaScript, изменить запрос или обратиться к API напрямую.

## 7.7. Подсказки и ошибки

```
<label for="password">Пароль</label>
<input
  id="password"
  name="password"
  type="password"
  aria-describedby="password-hint"
  required
>
<p id="password-hint">
  Минимум 8 символов.
</p>
```

Если возникла ошибка, она должна быть конкретной:

```
<p id="email-error">
  Введите корректный адрес электронной почты.
</p>
```

Неудачное сообщение:

```
Ошибка!
```

Хорошее сообщение объясняет:

- что именно не так;
- почему значение не принято;
- как исправить проблему.

## 7.8. `fieldset` и `legend`

Связанные элементы формы можно объединить:

```
<fieldset>
  <legend>Предпочитаемые жанры</legend>

  <label>
    <input type="checkbox" name="genre" value="fantasy">
    Фэнтези
  </label>

  <label>
    <input type="checkbox" name="genre" value="drama">
    Драма
  </label>
</fieldset>
```

`legend` сообщает смысл группы полей, что особенно полезно для пользователей вспомогательных технологий.

## 7.9. Кнопки формы

Внутри формы:

```
<button type="submit">Сохранить</button>
<button type="reset">Очистить</button>
<button type="button">Открыть справку</button>
```

Типы имеют различное поведение:

- `submit` отправляет форму;
- `reset` сбрасывает значения;
- `button` не выполняет стандартное действие и обычно управляется JavaScript.

Нужно явно указывать `type`, поскольку кнопка внутри `form` по умолчанию часто воспринимается как `submit`.

## 7.10. Клиентская и серверная валидация

Валидация на клиенте полезна для быстрого ответа пользователю:

```
<input
  type="email"
  required
  minlength="5"
>
```

Но она не является защитой данных. Правильная схема:

```
Frontend:
  быстро проверяет очевидные ошибки
       ↓
Backend:
  повторно проверяет всё перед обработкой
       ↓
Database:
  дополнительно защищает ограничения целостности
```

Например, даже если frontend запрещает отрицательный рейтинг, backend должен самостоятельно проверить это условие, поскольку клиентский код не является доверенным.

# 8. Семантические элементы

## 8.1. Что такое семантика

Семантика — это значение и роль элемента в структуре документа.

Сравним:

```
<div class="header">...</div>
```

и:

```
<header>...</header>
```

Оба элемента могут выглядеть одинаково после применения CSS, однако второй вариант сообщает браузеру, что содержимое является вводной или верхней частью страницы.

Семантическая разметка полезна для:

- программ чтения с экрана;
- навигации с клавиатуры;
- поисковых систем;
- анализа структуры документа;
- поддержки проекта;
- встроенного поведения браузера.

MDN рекомендует выбирать «правильный элемент для правильной задачи», поскольку семантические элементы предоставляют встроенные точки интеграции с доступностью.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML)][[developer.mozilla](https://developer.mozilla.org/en-US/curriculum/core/accessibility/)]

## 8.2. Основные структурные элементы

### `header`

```
<header>
  <a href="/" class="logo">Anime Catalog</a>
  <nav>
    ...
  </nav>
</header>
```

`header` представляет вводное или навигационное содержимое. Он может относиться ко всей странице или к отдельной секции.

### `nav`

```
<nav aria-label="Основная навигация">
  <ul>
    <li><a href="/">Главная</a></li>
    <li><a href="/catalog">Каталог</a></li>
    <li><a href="/about">О проекте</a></li>
  </ul>
</nav>
```

`nav` обозначает раздел с навигационными ссылками. Не каждый набор ссылок обязан находиться внутри `nav`: например, список внешних ссылок в подвале может не быть основной навигацией.

### `main`

```
<main>
  <h1>Каталог аниме</h1>
  ...
</main>
```

`main` содержит основное содержимое документа — то, ради чего пользователь открыл страницу. Обычно основной контент страницы должен быть представлен одним `main`.

### `section`

```
<section>
  <h2>Популярные сериалы</h2>
  ...
</section>
```

`section` объединяет тематически связанные элементы. Как правило, секция должна иметь заголовок.

Неправильно использовать `section` как универсальную замену `div` без смыслового раздела.

### `article`

```
<article>
  <h2>Fullmetal Alchemist</h2>
  <p>Описание произведения.</p>
</article>
```

`article` обозначает самостоятельный фрагмент, который потенциально можно отделить от остального контента:

- запись блога;
- новость;
- карточка товара;
- отзыв;
- публикация;
- комментарий.

### `aside`

```
<aside>
  <h2>Фильтры</h2>
  ...
</aside>
```

`aside` содержит дополнительный или косвенно связанный контент:

- боковую панель;
- фильтры;
- рекламный блок;
- справочную информацию;
- связанные ссылки.

### `footer`

```
<footer>
  <p>© 2026 Anime Catalog</p>
</footer>
```

`footer` содержит завершающую информацию страницы или секции:

- авторские права;
- контакты;
- дополнительные ссылки;
- сведения об авторе;
- навигацию.

Структурные элементы `header`, `nav`, `main`, `article`, `section`, `aside` и `footer` предназначены не для визуального позиционирования, а для описания ролей областей документа.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements)][[developer.mozilla](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/Structuring_documents)]

## 8.3. Пример семантической страницы

```
<body>
  <header>

# 9. Универсальные контейнеры `div` и `span`

## 9.1. `div`

`div` — нейтральный блочный контейнер. Он не сообщает специального смысла:

```
<div class="card">
  ...
</div>
```

Его уместно использовать:

- для группировки элементов ради CSS;
- для технического контейнера;
- когда подходящего семантического элемента действительно нет;
- для реализации визуальной сетки или компонента.

Не следует строить всю страницу из безымянных `div`:

```
<div class="header">
  <div class="menu">
    <div class="item">Главная</div>
  </div>
</div>
```

Если элементы являются шапкой, навигацией и ссылками, лучше выразить это напрямую:

```
<header>
  <nav>
    <a href="/">Главная</a>
  </nav>
</header>
```

## 9.2. `span`

`span` — нейтральный строчный контейнер:

```
<p>
  Рейтинг:
  <span class="rating">9.5</span>
</p>
```

Он полезен для:

- стилизации части текста;
- добавления технического идентификатора;
- обновления отдельного фрагмента через JavaScript;
- группировки строчного содержимого.

Как и `div`, `span` не следует использовать вместо элементов с готовой семантикой.

Неправильно:

```
<span class="button">Удалить</span>
```

Правильно:

```
<button type="button">Удалить</button>
```

# 10. Атрибуты HTML

## 10.1. Глобальные атрибуты

Глобальные атрибуты могут использоваться у многих HTML-элементов.

### `id`

```
<section id="reviews">
  ...
</section>
```

`id` должен быть уникальным в пределах документа. Он используется:

- для ссылок на фрагмент;
- связи `label` и `input`;
- связи ARIA-атрибутов;
- поиска элемента в JavaScript;
- стилизации, хотя для CSS чаще предпочтительнее классы.

Нельзя создавать два элемента с одинаковым `id`:

```
<div id="card"></div>
<div id="card"></div>
```

## 10.2. `class`

```
<article class="card card--featured">
  ...
</article>
```

`class` используется для объединения элементов по признаку или компоненту. В отличие от `id`, один класс может быть назначен множеству элементов, а один элемент может иметь несколько классов.

## 10.3. `title`

```
<button title="Удалить элемент">Удалить</button>
```

`title` может предоставлять дополнительную подсказку, но не должен быть единственным способом объяснить назначение элемента. На сенсорных устройствах такая подсказка может быть недоступна, а программы чтения с экрана обрабатывают её по-разному.

## 10.4. `hidden`

```
<section hidden>
  Содержимое появится после загрузки.
</section>
```

`hidden` сообщает, что элемент пока не является частью отображаемого содержимого. При необходимости JavaScript может удалить атрибут:

```
section.hidden = false;
```

## 10.5. `data-*`

```
<button
  type="button"
  data-anime-id="42"
>
  Открыть
</button>
```

Атрибуты `data-*` предназначены для хранения пользовательских данных, которые нужны скриптам:

```
const button = document.querySelector('button');
const animeId = button.dataset.animeId;
```

Не следует использовать `data-*` для замены стандартной семантики. Если элемент является кнопкой, он должен быть `button`, а не `div` с `data-action="button"`.

## 10.6. Булевы атрибуты

Некоторые атрибуты работают по принципу наличия:

```
<input type="email" required>
<button disabled>Сохранить</button>
<input type="checkbox" checked>
```

Важно:

```
<input required="false">
```

не означает «атрибут выключен». Наличие `required` уже активирует его, независимо от строкового значения. Для выключения атрибут нужно удалить:

```
<input>
```

# 11. Базовые правила доступности

## 11.1. Что такое доступность

Доступность означает, что веб-содержимое и интерфейс могут использовать люди с различными ограничениями, устройствами и способами взаимодействия.

Пользователь может:

- не видеть страницу;
- иметь ограниченное зрение;
- не пользоваться мышью;
- взаимодействовать только с клавиатурой;
- использовать экранный диктор;
- иметь когнитивные или моторные ограничения;
- работать с телефоном при ярком освещении;
- пользоваться нестабильным интернетом.

Доступность не является отдельной декоративной функцией: она начинается с корректной HTML-семантики.

## 11.2. Правильный элемент для правильной задачи

Основные соответствия:

|Задача|Правильный элемент|
|---|---|
|Перейти на другую страницу|`a`|
|Выполнить действие|`button`|
|Ввести текст|`input`, `textarea`|
|Выбрать значение|`select`, `input type="radio"`|
|Переключить независимый параметр|`input type="checkbox"`|
|Главный контент|`main`|
|Навигация|`nav`|
|Заголовок раздела|`h1`–`h6`|
|Изображение|`img`|
|Табличные данные|`table`|

Неправильный вариант:

```
<div onclick="removeItem()">Удалить</div>
```

Такой `div` не получает стандартного поведения кнопки: он может быть недоступен с клавиатуры, не будет корректно объявлен экранным диктором и не будет поддерживать ожидаемые состояния без дополнительного кода.

Правильный вариант:

```
<button type="button" onclick="removeItem()">
  Удалить
</button>
```

## 11.3. Клавиатурная навигация

Все интерактивные элементы должны быть доступны без мыши:

- ссылки;
- кнопки;
- поля форм;
- переключатели;
- элементы меню.

Проверка проста: открыть страницу и пройти по ней клавишей Tab. Пользователь должен понимать:

- какой элемент сейчас в фокусе;
- в каком порядке перемещается фокус;
- что произойдёт при нажатии Enter или Space.

Нельзя без необходимости убирать outline:

```
*:focus {
  outline: none;
}
```

Если стандартный фокус не устраивает визуально, его следует заменить заметным вариантом:

```
button:focus-visible,
a:focus-visible,
input:focus-visible {
  outline: 3px solid #2563eb;
  outline-offset: 2px;
}
```

## 11.4. Заголовки как навигационные ориентиры

Программа чтения с экрана позволяет перемещаться между заголовками. Поэтому заголовки должны отражать структуру, а не использоваться только ради размера шрифта.

Неправильно:

```
<h1>Каталог</h1>
<h4>Популярные</h4>
<h2>Новинки</h2>
```

Лучше:

```
<h1>Каталог</h1>
<h2>Популярные</h2>
<h2>Новинки</h2>
```

Уровень заголовка выбирается по структуре, а размер задаётся CSS.

## 11.5. Подписи к полям

Каждое поле, которое должен заполнить пользователь, должно иметь понятную подпись:

```
<label for="username">Имя пользователя</label>
<input id="username" name="username" type="text">
```

Placeholder не заменяет label:

```
<input
  type="email"
  placeholder="example@mail.com"
>
```

Placeholder исчезает после ввода и часто имеет низкий контраст. Он может использоваться как пример формата, но не как единственная подпись.

## 11.6. Цвет не должен быть единственным признаком

Плохо:

```
Красное поле означает ошибку, зелёное — успех.
```

Пользователь может не различать цвета или смотреть на экран в условиях, где оттенки плохо видны. Следует добавлять текст и, при необходимости, иконку:

```
Ошибка: введите корректный email.
```

## 11.7. Ясные названия ссылок и кнопок

Плохо:

```
<button>ОК</button>
<a href="/details">Подробнее</a>
```

если из контекста непонятно, что именно произойдёт.

Лучше:

```
<button type="submit">Сохранить профиль</button>
<a href="/anime/42">Подробнее о Fullmetal Alchemist</a>
```

## 11.8. ARIA — не замена HTML

ARIA позволяет дополнительно описывать роли, состояния и связи, но её не следует добавлять механически.

Плохой подход:

```
<div role="button">Удалить</div>
```

Если доступен настоящий элемент `button`, нужно использовать его:

```
<button type="button">Удалить</button>
```

ARIA особенно полезна для сложных компонентов, состояние которых нельзя выразить одним стандартным элементом, но основной принцип остаётся прежним:

> Сначала правильный HTML, затем ARIA только там, где нативной семантики недостаточно.

# 12. Типичные ошибки в HTML

## 12.1. Использование `div` вместо семантических элементов

Плохо:

```
<div class="header">
  <div class="navigation">
    <div class="link">Главная</div>
  </div>
</div>
```

Лучше:

```
<header>
  <nav>
    <a href="/">Главная</a>
  </nav>
</header>
```

## 12.2. Использование заголовков ради размера

Плохо:

```
<h3>Маленький серый текст</h3>
```

если это не заголовок.

Лучше:

```
<p class="small-text">Маленький серый текст</p>
```

CSS отвечает за внешний вид, HTML — за смысл.

## 12.3. Использование `br` для отступов

Плохо:

```
<h1>Каталог</h1>
<br><br><br>
<p>Описание</p>
```

Лучше:

```
<h1>Каталог</h1>
<p>Описание</p>
```

А расстояния задаются CSS:

```
h1 {
  margin-bottom: 2rem;
}
```

## 12.4. Изображение без `alt`

Плохо:

```
<img src="/images/poster.jpg">
```

Лучше:

```
<img
  src="/images/poster.jpg"
  alt="Постер аниме Fullmetal Alchemist"
>
```

Исключение — действительно декоративное изображение:

```
<img src="/images/decorative.svg" alt="">
```

## 12.5. Поле без подписи

Плохо:

```
<input type="email" placeholder="Email">
```

Лучше:

```
<label for="email">Электронная почта</label>
<input id="email" name="email" type="email">
```

## 12.6. Кнопка без `type`

Потенциально опасно:

```
<form>
  <button>Открыть подсказку</button>
</form>
```

Внутри формы кнопка может отправить её. Лучше:

```
<button type="button">Открыть подсказку</button>
```

## 12.7. Повторяющиеся `id`

Плохо:

```
<input id="title">
<input id="title">
```

`id` должен быть уникальным:

```
<input id="anime-title">
<input id="review-title">
```

## 12.8. Интерактивный элемент внутри интерактивного

Плохо:

```
<a href="/anime/42">
  <button type="button">Открыть</button>
</a>
```

Ссылка и кнопка выполняют разные интерактивные роли, и их вложенность создаёт неоднозначное поведение для клавиатуры и вспомогательных технологий.

Лучше выбрать один элемент:

```
<a href="/anime/42">Открыть</a>
```

или:

```
<button type="button">Открыть модальное окно</button>
```

## 12.9. Таблица для размещения элементов

Плохо использовать `table` для визуального макета:

```
<table>
  <tr>
    <td>Логотип</td>
    <td>Меню</td>
  </tr>
</table>
```

Таблицы предназначены для табличных данных, а расположение элементов следует строить с помощью CSS Grid или Flexbox.

## 12.10. Избыточное использование ARIA

Плохо:

```
<button role="button" aria-label="Кнопка">
  Удалить
</button>
```

Здесь `role="button"` избыточен, поскольку `button` уже имеет эту семантику, а `aria-label="Кнопка"` не объясняет действие.

Лучше:

```
<button type="button">
  Удалить
</button>
```

# Часть 3. CSS: стилизация и расположение элементов

Главная идея этой части:

> CSS не меняет смысл HTML-документа, а описывает правила его визуального представления и расположения элементов.

HTML отвечает на вопрос «что находится на странице», а CSS — «как это выглядит, где расположено и как меняется в зависимости от условий отображения». CSS описывает оформление и раскладку HTML-документа, а также может использоваться для разных сред вывода: экрана, печати и других способов представления.[[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/CSS)]

---

# 1. CSS как язык описания стилей

## 1.1. Зачем нужен CSS

Без CSS браузер всё равно сможет отобразить HTML, однако результат будет представлять собой преимущественно последовательность структурированных элементов с базовыми встроенными стилями.

Например:

```
<h1>Каталог аниме</h1>
<p>Подборка популярных произведений.</p>
<a href="/catalog">Открыть каталог</a>
```

Браузер покажет заголовок, абзац и ссылку, но разработчик не будет контролировать:

- используемый шрифт;
- размер текста;
- цвет;
- ширину контейнера;
- расположение блоков;
- количество колонок;
- отступы;
- адаптацию под телефон;
- визуальные состояния кнопок.

CSS позволяет выразить такие правила отдельно:

```
body {
  font-family: Arial, sans-serif;
  color: #1f2937;
  background-color: #f8fafc;
}

h1 {
  font-size: 2rem;
  margin-bottom: 1rem;
}

a {
  color: #2563eb;
}
```

HTML при этом сохраняет структуру:

```
<h1>Каталог аниме</h1>
<p>Подборка популярных произведений.</p>
<a href="/catalog">Открыть каталог</a>
```

Такое разделение позволяет менять внешний вид без изменения смысла документа.

## 1.2. CSS-правило

CSS-правило состоит из селектора и блока деклараций:

```
.card {
  color: #111827;
  background-color: white;
  padding: 1rem;
}
```

Здесь:

- `.card` — селектор;
- `{ ... }` — блок деклараций;
- `color` — CSS-свойство;
- `#111827` — значение свойства;
- `padding` — другое свойство;
- `1rem` — его значение.

Общая структура:

```
селектор {
  свойство: значение;
  свойство: значение;
}
```

Каждая декларация обычно заканчивается точкой с запятой:

```
p {
  color: #374151;
  line-height: 1.6;
}
```

Последняя точка с запятой технически может быть опущена, но сохранять её полезно: это уменьшает вероятность ошибок при добавлении новых правил и делает оформление единообразным.

## 1.3. Комментарии

Комментарии не влияют на отображение страницы:

```
/* Основные стили карточки */
.card {
  padding: 1rem;
}
```

Их следует использовать для пояснения решений, а не для комментария каждой очевидной строки:

```
/* Увеличиваем расстояние между карточками, чтобы они визуально не сливались */
.card {
  gap: 1rem;
}
```

Избыточные комментарии могут усложнить чтение, поэтому особенно полезны комментарии, объясняющие причину нестандартного решения.

# 2. Подключение CSS

## 2.1. Внешняя таблица стилей

Наиболее распространённый способ — подключить отдельный CSS-файл через `link`:

```
<head>
  <link rel="stylesheet" href="/styles/main.css">
</head>
```

Файл:

```
body {
  margin: 0;
  font-family: Arial, sans-serif;
}
```

Преимущества внешнего файла:

- стили отделены от HTML;
- один файл можно использовать на нескольких страницах;
- браузер может кэшировать CSS;
- проект проще поддерживать;
- структура документа не смешивается с оформлением.

## 2.2. Встроенные стили

Стили можно разместить внутри `style`:

```
<head>
  <style>
    body {
      margin: 0;
    }
  </style>
</head>
```

Это допустимо для небольших экспериментов, критических стилей или учебной демонстрации, но для полноценного проекта внешний файл обычно предпочтительнее.

## 2.3. Встроенный атрибут `style`

Стиль можно задать непосредственно элементу:

```
<p style="color: crimson;">Ошибка загрузки.</p>
```

Такой подход называется inline styles. Он может быть оправдан в отдельных динамических сценариях, но в обычной вёрстке имеет серьёзные недостатки:

- стили смешиваются со структурой;
- сложнее переиспользовать правила;
- сложнее переопределять значения;
- возрастает специфичность;
- ухудшается поддерживаемость.

Вместо этого лучше использовать класс:

```
<p class="error-message">Ошибка загрузки.</p>
```

```
.error-message {
  color: crimson;
}
```

## 2.4. Порядок загрузки

Обычно таблицы стилей подключают в `head`, чтобы браузер мог начать применять оформление до отображения основного содержимого:

```
<head>
  <meta charset="UTF-8">
  <link rel="stylesheet" href="/styles/main.css">
  <title>Каталог</title>
</head>
```

В учебном проекте достаточно начинать с одного файла:

```
frontend/
├── index.html
└── styles.css
```

Позже стили можно разделить:

```
styles/
├── reset.css
├── variables.css
├── layout.css
├── components.css
└── utilities.css
```

Не стоит дробить CSS заранее на десятки файлов без реальной необходимости: структура должна помогать ориентироваться, а не превращать простой проект в лабиринт.

# 3. Селекторы

Селектор определяет, к каким HTML-элементам применяются декларации.

## 3.1. Селектор элемента

```
p {
  color: #374151;
}
```

Правило применяется ко всем элементам `p`.

```
h1 {
  font-size: 2rem;
}
```

Такой селектор удобен для базовых правил, которые должны распространяться на все элементы определённого типа.

## 3.2. Селектор класса

```
<article class="card">
  ...
</article>
```

```
.card {
  border: 1px solid #e5e7eb;
}
```

Класс обозначается точкой:

```
.card { }
```

Классы — основной инструмент стилизации компонентов. Один класс может использоваться многократно:

```
<article class="card">...</article>
<article class="card">...</article>
<article class="card">...</article>
```

## 3.3. Селектор идентификатора

```
<header id="page-header">
  ...
</header>
```

```
#page-header {
  min-height: 64px;
}
```

Идентификатор обозначается символом `#`. Поскольку `id` должен быть уникальным, такой селектор подходит для конкретного элемента, но в больших проектах классы обычно удобнее для стилизации.

Практическое правило:

- `id` — уникальная идентификация элемента;
- `class` — переиспользуемая стилизация и группировка.

## 3.4. Универсальный селектор

```
* {
  box-sizing: border-box;
}
```

`*` выбирает все элементы.

Универсальный селектор полезен для базовых настроек, но не следует бездумно применять к нему тяжёлые или дорогие правила.

Один из распространённых вариантов:

```
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

## 3.5. Составные селекторы

Селекторы можно объединять:

```
.card.featured {
  border-color: #f59e0b;
}
```

Правило применяется к элементу, у которого одновременно есть классы `card` и `featured`.

```
button.primary {
  background-color: #2563eb;
}
```

Применяется к кнопке с классом `primary`.

## 3.6. Селектор потомка

```
.card p {
  color: #4b5563;
}
```

Правило выбирает все `p`, находящиеся внутри `.card`, независимо от глубины вложенности:

```
<article class="card">
  <div>
    <p>Описание карточки.</p>
  </div>
</article>
```

## 3.7. Селектор непосредственного ребёнка

```
.card > p {
  margin-top: 0;
}
```

Правило применяется только к `p`, являющемуся непосредственным ребёнком `.card`:

```
<article class="card">
  <p>Подходит.</p>

  <div>
    <p>Уже не подходит.</p>
  </div>
</article>
```

## 3.8. Соседние элементы

Соседний элемент:

```
h2 + p {
  margin-top: 0;
}
```

Правило применяется к абзацу, который непосредственно следует за `h2`.

Все последующие элементы того же уровня:

```
h2 ~ p {
  color: #4b5563;
}
```

## 3.9. Псевдоклассы

Псевдокласс описывает состояние элемента:

```
a:hover {
  color: #1d4ed8;
}

button:focus-visible {
  outline: 3px solid #93c5fd;
}

input:invalid {
  border-color: #dc2626;
}
```

Распространённые псевдоклассы:

- `:hover` — указатель находится над элементом;
- `:focus` — элемент получил фокус;
- `:focus-visible` — фокус следует явно показать;
- `:active` — элемент активируется;
- `:checked` — флажок или переключатель выбран;
- `:disabled` — элемент отключён;
- `:first-child` — первый ребёнок;
- `:last-child` — последний ребёнок;
- `:nth-child()` — элемент с определённой позицией.

Важно не полагаться только на `:hover`: на сенсорном устройстве нет классического указателя мыши, поэтому критически важная информация не должна быть доступна исключительно при наведении.

## 3.10. Псевдоэлементы

Псевдоэлементы обращаются к части элемента или создают декоративное содержимое:

```
.required::after {
  content: " *";
  color: crimson;
}
```

Распространённые псевдоэлементы:

- `::before`;
- `::after`;
- `::first-letter`;
- `::first-line`;
- `::placeholder`;
- `::selection`.

Псевдоэлементы удобны для декоративных деталей, но не следует помещать в `content` важный текст, который должен быть доступен пользователю и поисковым системам.

# 4. Каскад, специфичность и наследование

Название CSS расшифровывается как Cascading Style Sheets — каскадные таблицы стилей. Каскад означает, что браузер может получить несколько правил для одного элемента и должен определить, какие значения будут итоговыми.

## 4.1. Конфликт правил

HTML:

```
<p class="description">Описание произведения.</p>
```

CSS:

```
p {
  color: black;
}

.description {
  color: navy;
}
```

Оба правила подходят к элементу, но итоговым станет `navy`, поскольку селектор класса имеет большую специфичность, чем селектор элемента.

## 4.2. Источник стилей

На результат влияют разные источники:

- стандартные стили браузера;
- стили пользователя;
- стили автора страницы;
- inline-стили;
- специальные правила `!important`.

В обычной разработке основной контроль находится у таблиц стилей автора, однако встроенные стили браузера объясняют, почему у заголовков, ссылок, списков и кнопок уже есть начальное оформление.

## 4.3. Специфичность

Упрощённо специфичность можно представить как приоритет селекторов:

```
inline style
id
class / attribute / pseudo-class
element / pseudo-element
```

Пример:

```
p {
  color: black;
}

.description {
  color: navy;
}

#main-description {
  color: crimson;
}
```

```
<p id="main-description" class="description">
  Описание.
</p>
```

Итоговым будет `crimson`, поскольку `id` имеет большую специфичность.

Можно условно представить специфичность как четыре компонента:

```
(a, b, c, d)
```

где:

- `a` — inline-стили;
- `b` — количество идентификаторов;
- `c` — количество классов, атрибутов и псевдоклассов;
- `d` — количество элементов и псевдоэлементов.

Например:

```
#app .card p
```

имеет условную специфичность:

```
(0, 1, 1, 1)
```

## 4.4. Порядок при равной специфичности

Если два правила имеют одинаковую специфичность, побеждает правило, расположенное позже:

```
.title {
  color: navy;
}

.title {
  color: crimson;
}
```

Текст будет crimson.

Однако это правило применяется только при сопоставимой специфичности. Простое перемещение правила вниз не поможет, если другое правило значительно сильнее.

## 4.5. Наследование

Некоторые свойства передаются от родительского элемента к потомкам:

```
body {
  color: #1f2937;
  font-family: Arial, sans-serif;
}
```

Текстовые элементы внутри `body` обычно унаследуют цвет и шрифт, если для них не задано другое значение.

Чаще наследуются:

- `color`;
- `font-family`;
- `font-size`;
- `line-height`;
- некоторые свойства текста.

Обычно не наследуются автоматически:

- `margin`;
- `padding`;
- `border`;
- `width`;
- `height`;
- `background`.

Пример:

```
.card {
  color: navy;
  padding: 1rem;
}
```

Потомки карточки унаследуют `color`, но не получат автоматически `padding` самой карточки как собственный внутренний отступ.

## 4.6. Ключевые слова управления наследованием

```
.child {
  color: inherit;
}
```

`inherit` принудительно берёт значение у родителя.

```
.child {
  color: initial;
}
```

`initial` возвращает начальное значение свойства.

```
.child {
  color: unset;
}
```

`unset` ведёт себя как `inherit` для наследуемых свойств и как `initial` для ненаследуемых.

## 4.7. Почему `!important` опасен

```
.error {
  color: red !important;
}
```

`!important` повышает приоритет декларации и затрудняет последующее переопределение. Если использовать его повсеместно, разработчик постепенно начинает строить цепочку ещё более сильных правил.

Допустимо применять `!important` в редких инфраструктурных случаях, но обычный компонентный CSS лучше организовывать через:

- понятные классы;
- малую специфичность;
- предсказуемый порядок;
- слои CSS;
- локальные соглашения именования.

# 5. Цвета и шрифты

## 5.1. Цвет текста и фона

```
body {
  color: #1f2937;
  background-color: #f8fafc;
}
```

CSS поддерживает несколько форматов цветов.

### Именованные цвета

```
color: navy;
```

Подходят для простых примеров, но палитру проекта лучше задавать более точно.

### HEX

```
color: #2563eb;
```

HEX состоит из красной, зелёной и синей компонент:

```
#RRGGBB
```

Например:

```
#ff0000 — красный
#00ff00 — зелёный
#0000ff — синий
```

### RGB

```
color: rgb(37, 99, 235);
```

### HSL

```
color: hsl(217 91% 60%);
```

HSL разделяет:

- оттенок;
- насыщенность;
- светлоту.

### Прозрачность

```
background-color: rgb(37 99 235 / 0.15);
```

Последнее значение задаёт альфа-канал.

## 5.2. Контраст

Цвет текста должен быть достаточно контрастным относительно фона. Светло-серый текст на белом фоне может выглядеть эстетично, но быть трудным для чтения.

Не следует кодировать смысл только цветом:

```
красное — ошибка;
зелёное — успех.
```

Лучше добавить текстовое состояние:

```
<p class="status status--error">
  Ошибка: не удалось загрузить данные.
</p>
```

```
.status--error {
  color: #b91c1c;
}
```

## 5.3. `font-family`

```
body {
  font-family: Arial, sans-serif;
}
```

В качестве запасных вариантов указывают fallback:

```
body {
  font-family: Inter, Arial, sans-serif;
}
```

Если шрифт `Inter` недоступен, браузер попробует `Arial`, а затем любой доступный шрифт без засечек.

Системный стек:

```
body {
  font-family:
    system-ui,
    -apple-system,
    BlinkMacSystemFont,
    "Segoe UI",
    sans-serif;
}
```

## 5.4. Подключение веб-шрифта

```
@font-face {
  font-family: "Project Sans";
  src: url("/fonts/project-sans.woff2") format("woff2");
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}
```

```
body {
  font-family: "Project Sans", sans-serif;
}
```

Шрифт увеличивает объём ресурсов, поэтому важно учитывать:

- размер файла;
- поддерживаемые начертания;
- формат `woff2`;
- время загрузки;
- fallback;
- необходимость preload только для действительно критических шрифтов.

## 5.5. Размер текста

```
body {
  font-size: 1rem;
}

h1 {
  font-size: 2rem;
}
```

Размеры можно задавать в:

- `px`;
- `rem`;
- `em`;
- `%`;
- `vw`;
- `clamp()`.

`rem` связан с размером шрифта корневого элемента:

```
html {
  font-size: 16px;
}

p {
  font-size: 1rem;
}
```

Обычно `1rem` равен базовому размеру шрифта браузера, если пользователь его не изменил.

`em` зависит от размера шрифта текущего элемента или родителя, поэтому при вложенности может накапливать эффект:

```
.parent {
  font-size: 1.2em;
}

.child {
  font-size: 1.2em;
}
```

Для масштабирования интерфейса `rem` часто предсказуемее.

## 5.6. Свойства текста

```
.description {
  font-size: 1rem;
  font-weight: 400;
  line-height: 1.6;
  letter-spacing: 0.01em;
  text-align: left;
}
```

Основные свойства:

- `font-size`;
- `font-family`;
- `font-weight`;
- `font-style`;
- `line-height`;
- `letter-spacing`;
- `text-align`;
- `text-decoration`;
- `text-transform`.

Для основного текста обычно важнее хорошая высота строки, чем чрезмерно плотная компоновка:

```
body {
  line-height: 1.5;
}
```

## 5.7. `clamp()`

Для плавного изменения размера можно использовать:

```
h1 {
  font-size: clamp(1.75rem, 4vw, 3rem);
}
```

Это означает:

- минимум `1.75rem`;
- гибкое значение около `4vw`;
- максимум `3rem`.

Такой подход позволяет уменьшить количество резких breakpoint’ов.

# 6. Блочная модель

## 6.1. Из чего состоит CSS-блок

Каждый элемент можно представить как прямоугольную область, состоящую из четырёх частей:

```
┌──────────────────────────────┐
│           margin             │
│  ┌────────────────────────┐  │
│  │        border          │  │
│  │  ┌──────────────────┐  │  │
│  │  │     padding      │  │  │
│  │  │  ┌────────────┐  │  │  │
│  │  │  │  content   │  │  │  │
│  │  │  └────────────┘  │  │  │
│  │  └──────────────────┘  │  │
│  └────────────────────────┘  │
└──────────────────────────────┘
```

Части:

1. `content` — содержимое;
2. `padding` — внутренний отступ;
3. `border` — граница;
4. `margin` — внешний отступ.

## 6.2. Content box

По умолчанию ширина и высота относятся только к содержимому:

```
.card {
  width: 300px;
  padding: 20px;
  border: 2px solid black;
}
```

Фактическая ширина:

```
300 + 20 + 20 + 2 + 2 = 344 пикселя
```

Такое поведение часто приводит к неожиданным переполнениям.

## 6.3. `box-sizing: border-box`

Обычно удобно установить:

```
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

Теперь заданная ширина включает содержимое, padding и border:

```
.card {
  width: 300px;
  padding: 20px;
  border: 2px solid black;
}
```

Внешний размер по ширине будет равен 300 пикселям, а область содержимого уменьшится с учётом внутренних отступов и границы.

Это не отменяет свойства `margin`: внешний отступ по-прежнему добавляется за пределами ширины элемента.

## 6.4. Padding

```
.card {
  padding: 1rem;
}
```

Можно задавать значения по сторонам:

```
.card {
  padding-top: 1rem;
  padding-right: 1.5rem;
  padding-bottom: 1rem;
  padding-left: 1.5rem;
}
```

Сокращённые записи:

```
padding: 1rem;
```

Все стороны.

```
padding: 1rem 2rem;
```

Вертикаль / горизонталь.

```
padding: 1rem 2rem 1.5rem;
```

Верх / горизонталь / низ.

```
padding: 1rem 1.5rem 2rem 2.5rem;
```

Верх / право / низ / лево — по часовой стрелке.

## 6.5. Margin

```
.card {
  margin-bottom: 1rem;
}
```

Margin создаёт пространство между элементом и соседями.

Центрирование блочного элемента:

```
.container {
  max-width: 1200px;
  margin-inline: auto;
}
```

`margin-inline: auto` распределяет свободное место по горизонтали, если у элемента есть ограниченная ширина.

## 6.6. `border`

```
.card {
  border: 1px solid #e5e7eb;
}
```

Граница состоит из:

- толщины;
- стиля;
- цвета.

Можно задавать части отдельно:

```
.card {
  border-width: 1px;
  border-style: solid;
  border-color: #e5e7eb;
}
```

## 6.7. Скругление и тени

```
.card {
  border-radius: 12px;
  box-shadow: 0 8px 24px rgb(15 23 42 / 0.08);
}
```

Скругление и тень являются визуальными свойствами и не меняют семантику элемента.

## 6.8. Размеры и переполнение

```
.card {
  width: 100%;
  max-width: 360px;
  min-height: 220px;
}
```

Основные свойства:

- `width`;
- `height`;
- `min-width`;
- `max-width`;
- `min-height`;
- `max-height`;
- `overflow`.

Если содержимое не помещается:

```
.card {
  overflow: hidden;
}
```

Но `overflow: hidden` нельзя использовать как универсальное средство исправления вёрстки: он может скрыть важный текст, фокус или интерактивный элемент.

# 7. Поток документа и `display`

## 7.1. Нормальный поток

По умолчанию элементы располагаются в normal flow — обычном потоке документа.

Блочные элементы обычно занимают доступную ширину и располагаются друг под другом:

```
<div>Первый</div>
<div>Второй</div>
```

Строчные элементы располагаются внутри строки:

```
<span>Первый</span>
<span>Второй</span>
```

## 7.2. `display: block`

```
.badge {
  display: block;
}
```

Элемент начинает вести себя как блочный.

## 7.3. `display: inline`

```
.badge {
  display: inline;
}
```

Элемент располагается внутри строки. Для inline-элементов ширина и высота ведут себя не так, как у блоков.

## 7.4. `display: inline-block`

```
.badge {
  display: inline-block;
  padding: 0.25rem 0.5rem;
}
```

Элемент остаётся в строковом контексте, но получает возможность корректно применять ширину, высоту, padding и border.

## 7.5. `display: none`

```
.hidden {
  display: none;
}
```

Элемент удаляется из визуального потока и не занимает место.

Это отличается от:

```
.invisible {
  visibility: hidden;
}
```

`visibility: hidden` скрывает элемент, но сохраняет его место в раскладке. Оба варианта имеют разные последствия для доступности и взаимодействия, поэтому выбор должен соответствовать задаче.

# 8. Flexbox

## 8.1. Назначение Flexbox

Flexbox предназначен прежде всего для одномерной раскладки: работы с элементами вдоль одной главной оси — строки или столбца.

Он особенно полезен для:

- навигационных панелей;
- рядов кнопок;
- выравнивания иконки и текста;
- карточек с одинаковыми внутренними областями;
- вертикального расположения элементов;
- распределения свободного места.

MDN описывает Flexbox как механизм гибкого размещения элементов вдоль одной оси, тогда как Grid ориентирован на двумерную раскладку строк и столбцов.[[developer.mozilla](https://developer.mozilla.org/en-US/curriculum/core/css-layout/)]

## 8.2. Flex-контейнер

```
.nav-list {
  display: flex;
}
```

После `display: flex` непосредственные дети `.nav-list` становятся flex-элементами:

```
<nav class="nav-list">
  <a href="/">Главная</a>
  <a href="/catalog">Каталог</a>
  <a href="/about">О проекте</a>
</nav>
```

## 8.3. Главная и поперечная оси

По умолчанию:

```
flex-direction: row;
```

Главная ось идёт слева направо, а поперечная — сверху вниз.

```
Главная ось →
┌────────┬────────┬────────┐
│ item 1 │ item 2 │ item 3 │
└────────┴────────┴────────┘
```

Если задать:

```
flex-direction: column;
```

главная ось станет вертикальной.

## 8.4. `justify-content`

`justify-content` управляет распределением элементов вдоль главной оси:

```
.nav-list {
  display: flex;
  justify-content: space-between;
}
```

Основные значения:

```
justify-content: flex-start;
justify-content: center;
justify-content: flex-end;
justify-content: space-between;
justify-content: space-around;
justify-content: space-evenly;
```

Пример:

```
.header {
  display: flex;
  justify-content: space-between;
  align-items: center;
}
```

Логотип окажется слева, а меню — справа, при этом элементы будут выровнены по поперечной оси.

## 8.5. `align-items`

`align-items` управляет выравниванием по поперечной оси:

```
.header {
  display: flex;
  align-items: center;
}
```

Основные значения:

```
align-items: stretch;
align-items: flex-start;
align-items: center;
align-items: flex-end;
```

Для горизонтального ряда `align-items: center` обычно выравнивает элементы по вертикали.

## 8.6. `gap`

```
.nav-list {
  display: flex;
  gap: 1rem;
}
```

`gap` задаёт расстояние между flex-элементами. Он обычно лучше, чем добавление `margin` каждому элементу:

```
.nav-list a {
  margin-right: 1rem;
}
```

При использовании margin приходится отдельно обрабатывать последний элемент, а `gap` выражает именно расстояние между соседями.

## 8.7. Перенос элементов

```
.tag-list {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem;
}
```

Без `flex-wrap` элементы могут пытаться уместиться в одну строку и выйти за пределы контейнера.

## 8.8. `flex`

```
.card-content {
  display: flex;
  flex-direction: column;
  min-height: 100%;
}

.card-actions {
  margin-top: auto;
}
```

`margin-top: auto` в flex-колонке может прижать блок действий к низу карточки.

Другой пример:

```
.sidebar {
  flex: 0 0 280px;
}

.content {
  flex: 1;
}
```

Здесь sidebar получает фиксированную базовую ширину, а content занимает оставшееся пространство.

## 8.9. Типичная ошибка Flexbox

```
.container {
  display: flex;
  justify-content: center;
}
```

Разработчик ожидает вертикального центрирования, но `justify-content` действует по главной оси. При направлении `row` это горизонтальное центрирование.

Для полного центрирования:

```
.container {
  display: flex;
  justify-content: center;
  align-items: center;
}
```

Если направление `column`, поведение осей поменяется:

```
.container {
  display: flex;
  flex-direction: column;
  justify-content: center;
  align-items: center;
}
```

# 9. CSS Grid

## 9.1. Назначение Grid

CSS Grid предназначен для двумерной раскладки, в которой нужно управлять строками и столбцами одновременно:

- каталоги карточек;
- страницы с боковой панелью;
- сложные сетки;
- дашборды;
- макет страницы;
- области с явно заданной структурой.

## 9.2. Простейшая сетка

```
.catalog {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 1rem;
}
```

```
┌────────┬────────┬────────┐
│ card 1 │ card 2 │ card 3 │
├────────┼────────┼────────┤
│ card 4 │ card 5 │ card 6 │
└────────┴────────┴────────┘
```

`1fr` означает одну долю доступного пространства.

## 9.3. Фиксированные и гибкие колонки

```
.layout {
  display: grid;
  grid-template-columns: 280px 1fr;
  gap: 2rem;
}
```

Первая колонка имеет ширину 280 пикселей, вторая занимает остаток.

```
.layout {
  grid-template-columns: minmax(200px, 280px) 1fr;
}
```

`minmax()` задаёт диапазон допустимых размеров.

## 9.4. Автоматическое заполнение

Для карточек часто удобно использовать:

```
.catalog {
  display: grid;
  grid-template-columns: repeat(
    auto-fit,
    minmax(220px, 1fr)
  );
  gap: 1rem;
}
```

Браузер автоматически размещает столько колонок, сколько помещается в контейнере, а затем переносит карточки на новые строки.

Можно использовать `auto-fill`; разница проявляется при наличии свободного места и пустых потенциальных треков:

- `auto-fit` растягивает существующие колонки;
- `auto-fill` сохраняет доступные треки, даже если они пока пусты.

Для первого курса достаточно закрепить практический паттерн `auto-fit + minmax()`.

## 9.5. Области Grid

```
.page {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-areas:
    "header header"
    "sidebar content"
    "footer footer";
}

.header {
  grid-area: header;
}

.sidebar {
  grid-area: sidebar;
}

.content {
  grid-area: content;
}

.footer {
  grid-area: footer;
}
```

Такой подход позволяет описывать макет именованными областями, что часто повышает читаемость.

## 9.6. Grid и Flexbox: как выбирать

|Задача|Предпочтительный инструмент|
|---|---|
|Ряд кнопок|Flexbox|
|Навигация|Flexbox|
|Выравнивание иконки и текста|Flexbox|
|Каталог карточек|Grid|
|Страница с колонками|Grid|
|Двумерная таблица макета|Grid|
|Вертикальная группа элементов|Flexbox|
|Сложная сетка областей|Grid|

Это не жёсткий запрет: Flexbox способен создавать переносы, а Grid может раскладывать элементы в одну строку. Однако выбор по основной геометрии помогает сделать код понятнее.

# 10. Адаптивность

## 10.1. Что такое адаптивный интерфейс

Адаптивный интерфейс изменяет раскладку и размеры в зависимости от условий, в которых он отображается:

- ширины viewport;
- высоты viewport;
- ориентации;
- плотности пикселей;
- типа устройства;
- пользовательских предпочтений;
- доступного пространства.

Современный адаптивный дизайн не означает создание отдельной «мобильной версии» на другом URL. Обычно используется одна HTML-структура, а CSS адаптирует её представление.

Responsive design рассматривает сайт как интерфейс, который должен корректно работать на различных размерах и разрешениях экрана, а media queries позволяют условно применять стили в зависимости от среды просмотра.[[mdn2.netlify](https://mdn2.netlify.app/en-us/docs/learn/css/css_layout/responsive_design/)][[developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Using)]

## 10.2. Flexible layout

Адаптивность начинается не с media queries, а с гибких основ:

```
.container {
  width: 100%;
  max-width: 1200px;
  margin-inline: auto;
  padding-inline: 1rem;
}
```

Изображения:

```
img {
  display: block;
  max-width: 100%;
  height: auto;
}
```

Карточки:

```
.card {
  width: 100%;
}
```

Плохой подход:

```
.card {
  width: 480px;
}
```

Фиксированная ширина может привести к горизонтальной прокрутке на телефоне.

## 10.3. Mobile-first

Mobile-first означает, что базовые стили разрабатываются для узкого экрана, а затем расширяются для больших экранов:

```
.catalog {
  display: grid;
  grid-template-columns: 1fr;
  gap: 1rem;
}

@media (min-width: 768px) {
  .catalog {
    grid-template-columns: repeat(2, 1fr);
  }
}

@media (min-width: 1100px) {
  .catalog {
    grid-template-columns: repeat(3, 1fr);
  }
}
```

Преимущества:

- мобильная версия не является второстепенной;
- базовый CSS проще;
- добавляются только необходимые улучшения;
- меньше переопределений;
- проще контролировать производительность и доступность.

## 10.4. Breakpoint не равен модели устройства

Не следует выбирать breakpoint только по названиям устройств:

```
/* iPhone */
@media (min-width: 390px) { }

/* Tablet */
@media (min-width: 768px) { }
```

Размеры и ориентации устройств различаются, а окно браузера может быть произвольной ширины. Breakpoint должен появляться тогда, когда текущая композиция перестаёт быть удобной.

Правильный вопрос:

> При какой ширине меню, карточки или текст перестают помещаться без ухудшения интерфейса?

## 10.5. Media queries

Базовый синтаксис:

```
@media (min-width: 768px) {
  .layout {
    grid-template-columns: 240px 1fr;
  }
}
```

Правило применяется, если ширина viewport не меньше 768 пикселей.

Можно использовать несколько условий:

```
@media screen and (min-width: 768px) and (orientation: landscape) {
  .hero {
    min-height: 60vh;
  }
}
```

Медиа-запросы могут учитывать:

- ширину;
- высоту;
- ориентацию;
- тип вывода;
- плотность;
- пользовательские предпочтения;
- уменьшение анимации;
- светлую или тёмную тему.

## 10.6. Предпочтение уменьшенного движения

```
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms;
    animation-iteration-count: 1;
    transition-duration: 0.01ms;
    scroll-behavior: auto;
  }
}
```

Если пользователь включил системную настройку уменьшения движения, интерфейс должен избегать навязчивых анимаций.

## 10.7. Тёмная тема

```
@media (prefers-color-scheme: dark) {
  :root {
    color-scheme: dark;
  }

  body {
    background: #111827;
    color: #f9fafb;
  }
}
```

Это демонстрирует, что media queries могут учитывать не только размеры экрана, но и пользовательские предпочтения.

# 11. CSS-переменные

Для проекта удобно выносить повторяющиеся значения в custom properties:

```
:root {
  --color-primary: #2563eb;
  --color-text: #1f2937;
  --color-muted: #6b7280;
  --color-border: #e5e7eb;
  --space-sm: 0.5rem;
  --space-md: 1rem;
  --space-lg: 2rem;
  --radius-md: 0.75rem;
}
```

Использование:

```
.card {
  color: var(--color-text);
  border: 1px solid var(--color-border);
  border-radius: var(--radius-md);
  padding: var(--space-md);
}
```

Преимущества:

- единая цветовая система;
- удобное изменение темы;
- меньше повторений;
- более выразительные правила.

Переменные наследуются, поэтому их можно переопределять на уровне компонента:

```
.card--featured {
  --color-border: #f59e0b;
  border-color: var(--color-border);
}
```

Можно задать fallback:

```
color: var(--color-primary, blue);
```

Если переменная не определена, будет использовано `blue`.

# 13. Типичные ошибки в CSS

## 13.1. Слишком много фиксированных размеров

Плохо:

```
.page {
  width: 1440px;
}

.card {
  width: 400px;
}
```

На маленьком экране это приведёт к переполнению.

Лучше:

```
.page {
  width: min(100% - 2rem, 1200px);
}

.card {
  width: 100%;
}
```

## 13.2. Использование `!important` для исправления всего

Плохо:

```
.title {
  color: black !important;
}
```

а затем:

```
.title {
  color: navy !important;
}
```

Постепенно код превращается в борьбу приоритетов. Лучше разобраться, какое правило должно быть ответственным за стиль и почему конфликт возник.

## 13.3. Большие отступы через `br`

Плохо:

```
<h1>Каталог</h1>
<br><br>
<p>Описание</p>
```

Отступы относятся к CSS:

```
h1 {
  margin-bottom: 2rem;
}
```

## 13.4. Неправильное использование `height: 100%`

```
.card {
  height: 100%;
}
```

Процентная высота зависит от вычисленной высоты родителя. Если у родителя высота не задана, результат может оказаться не таким, как ожидается.

Для карточек часто лучше использовать:

```
.card {
  min-height: 100%;
}
```

и корректно настроить контейнер.

## 13.5. Горизонтальная прокрутка

Причины:

- фиксированная ширина;
- слишком длинная строка;
- изображение без `max-width`;
- отрицательные margins;
- grid-колонка, не способная сжаться;
- `width: 100vw` вместе с вертикальной полосой прокрутки;
- длинный URL или слово без переноса.

Для Grid часто полезно:

```
.grid {
  grid-template-columns: repeat(3, minmax(0, 1fr));
}
```

`minmax(0, 1fr)` позволяет колонке действительно сжиматься, а не сохранять минимальную ширину содержимого.

## 13.6. Потеря фокуса

Плохо:

```
button:focus {
  outline: none;
}
```

Если необходимо изменить стандартный фокус:

```
button:focus-visible {
  outline: 3px solid #2563eb;
  outline-offset: 2px;
}
```

## 13.7. Адаптивность только для одного устройства

Плохо проектировать только:

```
телефон 375 px
компьютер 1440 px
```

между ними есть множество промежуточных размеров. Лучше строить гибкую основу, а breakpoint добавлять тогда, когда композиция действительно требует перестройки.

# 14. Проверка CSS

## 14.1. Что проверять

- нет ли горизонтальной прокрутки;
- читается ли текст на маленьком экране;
- виден ли фокус клавиатуры;
- не перекрываются ли элементы;
- не выходит ли изображение за пределы контейнера;
- корректно ли работает при увеличении шрифта;
- не зависит ли интерфейс только от hover;
- сохраняется ли логическая структура при изменении расположения;
- не скрыт ли важный контент через `overflow: hidden`;
- не нарушается ли контраст.

## 14.2. DevTools

Вкладка Elements позволяет:

- видеть применённые правила;
- находить зачёркнутые декларации;
- проверять специфичность;
- временно изменять значения;
- смотреть box model;
- проверять размеры и computed styles;
- включать режим адаптивного устройства;
- имитировать состояния `:hover` и `:focus`.

## 14.3. Проверка без CSS

Временно отключив CSS, можно проверить:

- логичен ли порядок контента;
- присутствуют ли все заголовки;
- понятны ли ссылки;
- не спрятана ли важная информация исключительно в декоративных элементах;
- корректно ли работает документ на базовом уровне.

Хорошая CSS-вёрстка улучшает структурированный HTML, а не маскирует отсутствие структуры.
